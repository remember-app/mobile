# Remember — мобильное приложение

Expo / React Native (TypeScript), iOS + Android. Единственный клиент продукта; общается только с
`api`. Общий пакет типов с `api` не заводится — нужные типы дублируются здесь (`src/api/`).

Сейчас здесь клиент аккаунтов (m-3): вход тремя способами, токен сессии в `expo-secure-store`
(Keychain на iOS, EncryptedSharedPreferences на Android), ник, профиль, выход — и гейт, который
решает, какие экраны вообще существуют. Поверх него — воспоминания: список своих на главной,
создание нового, само воспоминание одним экраном без вкладок (лента кадров, «Ролики» первым блоком
над ней) и его настройки отдельным экраном — люди, обложка, название, даты, — плюс выбор кадров на
телефоне. Что где стоит — см. ниже.

**Экраны сейчас в переходном состоянии.** Библиотека деталей собрана по новому макету «Афиша»
(`design/spec.md`), а расстановка на части экранов осталась от прежней — её переписывают задачи
вехи, по экрану на задачу. То есть внешность деталей уже новая, а компоновка ещё не везде; разбирая
такой экран, не сверяйтесь с ним как с образцом — сверяйтесь со спекой. Собраны заново и сверены с
макетом: главный экран и создание (`src/app/index.tsx`, `src/app/create.tsx`, TASK-143), пять
экранов входа (`login`, `login/email`, `login/code`, `consent`, `set-username`, TASK-160; по
выгрузке 27 сентября — TASK-425), окно
открытого кадра со своими листами (`src/screens/memory/frame-viewer.tsx`, TASK-211), настройки
воспоминания с его правкой (`memory/[id]/settings`, `memory/[id]/edit`, TASK-209) и само
воспоминание (`src/app/memory/[id].tsx` с `src/screens/memory/`, TASK-207). У всех них каркас — `Board`
кита, а не свой `View` с отступом под строку статуса; у самого воспоминания каркаса нет вовсе —
там лента во всю ширину, а шапка и подвал висят над ней.

Из трёх входов вживую работает только почта. Apple и Google подключены целиком, но им нужны ключи
на стороне `api` — без них он отвечает `501` — и **dev-билд**: в Expo Go нет ни entitlement на
Sign in with Apple, ни нашей URL-схемы. Кнопке Google нужен вдобавок
`EXPO_PUBLIC_GOOGLE_CLIENT_ID`.

Экран входа показывает только те входы, которыми можно пройти, и решают это двое. Сервер — ответом
`GET /auth/methods` (`{ email, apple, google }`): вход, которого он не включил, не рисуется. Сборка
и телефон — кнопки Apple нет там, где `AppleAuthentication.isAvailableAsync()` отвечает `false`,
кнопки Google — там, где не задан `EXPO_PUBLIC_GOOGLE_CLIENT_ID`. Почта стоит всегда и с первого
кадра; пока сервер не ответил, а если он не ответил вовсе — то и навсегда, она одна. Все три кнопки
одного размера: на этом экране акцента нет вовсе — какой вход чей, приложению знать неоткуда. Отказ
`501` от сервера обрабатывается по-прежнему: ответ о способах может устареть, и тогда отвечать
приходится словами.

Вход по почте — шесть цифр из письма (`login/email` → `login/code`), а не ссылка: сервер перестал
её слать (TASK-138). Перед первым ником стоит соглашение (`consent`): `POST /me/username` без него
отвечает `403`, поэтому гейт ставит экран соглашения первым, а форма ника на этот отказ уводит
обратно к нему, а не печатает его.

## Где что лежит

```
src/
  app/              маршруты Expo Router — только они, и там, где их ждёт роутер
  kit/              библиотека деталей: одна деталь — один файл, рядом её история
  screens/          то, из чего собраны экраны, но что маршрутом не является
    memory/           воспоминание: лента, ролики, окно кадра, листы над ними
    order/            каркас заказа ролика, в котором стоят его шаги
    upload/           плёнка телефона и тело экрана загрузки без ленты
    mine/             лист своего кадра на «Мои кадры»
    onboarding/       общая шапка первых экранов и форма ника
  api/              всё, чем приложение говорит с сервером — по семье маршрутов на файл
  strings/          словарь: по файлу на раздел, в порядке, в каком приложение проходят
  theme/            токены «Афиши» и то, в какой из двух тем приложение сейчас
  lib/              домашние модули без экрана: даты, место, язык, лента, ролик, загрузка
  types/            объявления для бандлера — картинка, `?raw`
tests/              тесты той же раскладкой; общее — в tests/helpers/
```

Правило одно: под `src/app/` лежат только маршруты, потому что Expo Router делает маршрут из
каждого файла в этой папке. Всё остальное — по области. `@/…` ведёт в `src/`, `@tests/…` — в
`tests/`.

## Требования

- Node 20+
- Expo Go на телефоне **или** iOS-симулятор / Android-эмулятор
- Запущенный `api` (соседний репозиторий) — без него не войти, а главный экран вместо списка
  покажет ошибку и кнопку «Try again»

## Запуск

```sh
npm install
EXPO_PUBLIC_API_URL=http://localhost:3000 npx expo start
```

Дальше — `i` (iOS-симулятор), `a` (Android-эмулятор) или QR-код в Expo Go.

Чтобы не писать переменную каждый раз, положите её в `.env` (файл в `.gitignore`):

```sh
EXPO_PUBLIC_API_URL=http://localhost:3000
```

### `EXPO_PUBLIC_API_URL`

Базовый URL API. Без неё берётся `http://localhost:3000`.

`localhost` работает только на симуляторе/эмуляторе. **С телефона через Expo Go** подставьте
IP машины в локальной сети, например `EXPO_PUBLIC_API_URL=http://192.168.1.10:3000`.

Переменная подставляется в бандл на сборке — после её изменения перезапустите `expo start`.
По той же причине в `EXPO_PUBLIC_*` не кладутся секреты: содержимое уезжает в собранное приложение.

### Код входа по email в разработке

Когда на API явно включён `EMAIL_LOGIN_DEV_BYPASS` (значение `1` или `true`), адрес — на домене
`test.test`, а сам API не в проде, `POST /auth/email/start` отдаёт сам код прямо в ответе вместо
письма. Экран почты передаёт его дальше, в шесть ячеек, и они открываются заполненными под плашкой
«вход для разработки»: руками делать нечего — адрес, «Отправить код», «Подтвердить».

Нужны все три условия сразу. Ключи почты (`RESEND_API_KEY`, `MAIL_FROM`) на обход больше не
влияют: с любым другим адресом уходит настоящее письмо, а без ключей приходит 503.

В лог код не пишется, это ключ от аккаунта. Если он нужен отдельно — возьмите его из ответа:

```sh
curl -s localhost:3000/auth/email/start \
  -H 'content-type: application/json' -d '{"email":"you@test.test"}'
```

Схема `remember://` осталась только у приглашений (`remember://invite?token=…`) и работает лишь в
dev-билде: в Expo Go она принадлежит не нам, и `xcrun simctl openurl booted "remember://…"` падает
с `LSApplicationWorkspaceErrorDomain 115`. В Expo Go тот же экран открывается через схему Expo
(`exp://127.0.0.1:8081/--/invite?token=…`).

## Пуши

Код целиком в `src/lib/push.ts` (хук `usePush()` в корневом навигаторе): после входа спрашивается
разрешение, токен уходит в `POST /me/push-tokens`, тап по пушу «вас позвали» открывает
`/memory/[id]/upload` того воспоминания. Пуш «ролик готов» несёт, кроме `montageId`, ещё и
`memoryId` — по нему открывается само воспоминание, где ролики стоят первым блоком ленты, новый
среди них: досылать туда нечего.
Не получилось — в логе Metro строка
`push registration skipped: …` (нет `projectId`, отказ в разрешении, симулятор); экрана про это
нет и не будет: пуш — не единственный способ узнать о приглашении.

**В Expo Go удалённых пушей нет** (с SDK 53), нужен dev-билд — поэтому в зависимостях
`expo-dev-client`, а в `eas.json` профиль `development`.

Чтобы это заработало вживую, нужен Expo-аккаунт — **этого шага здесь нет, и в коде ничего не
зашито**:

1. `eas init` в этой папке (глобальный `eas` — `npm i -g eas-cli`; `npx eas` тянет чужой пакет) —
   он и запишет `expo.extra.eas.projectId` (и `owner`) в `app.json`.
   Именно это поле читает `getExpoPushTokenAsync`; без него в логе `No "projectId" found`.
2. `ios.bundleIdentifier` и `android.package` в `app.json` — их спросит первая `eas build` и
   запишет сама.
3. `eas build --profile development -p ios` (или `android`), поставить сборку на телефон,
   `npx expo start --dev-client`. Переменные (`EXPO_PUBLIC_API_URL`) dev-билд берёт с дев-сервера,
   то есть из локального `.env`, а не из сборки.
4. Ключи APNs / FCM — `eas credentials`.

Плагин `expo-notifications` ставит `aps-environment: development`; в сборке для магазина Xcode
сам меняет его на `production`, отдельной настройки для TestFlight нет.

## Раздача через TestFlight

Профиль `testflight` в `eas.json` собирает приложение для магазина и вшивает в него адрес сервера
`https://dev-api-remember.noxlabs.xyz` — это `EXPO_PUBLIC_API_URL` самого профиля; локальный `.env`
в облачную сборку не попадает. Номер сборки EAS поднимает сам и пишет в `app.json`
(`ios.buildNumber`); его надо коммитить — App Store Connect не примет вторую сборку с тем же номером.

Всё ниже делает человек, из этой папки, глобальным `eas` (`npm i -g eas-cli`). Первый раз — по
порядку; на каждую следующую сборку — шаги 5 и 6.

1. Сервер отвечает снаружи — адрес вшивается в сборку, и с лежащим сервером она бесполезна:
   ```sh
   curl https://dev-api-remember.noxlabs.xyz/health   # {"status":"ok"}
   ```
2. Вход в Expo — аккаунтом с доступом к организации `nox-labs`:
   ```sh
   eas login
   ```
3. Подпись и ключ пушей. Команда попросит профиль (`testflight`) и вход в Apple Developer — Apple
   ID, пароль, код подтверждения:
   ```sh
   eas credentials -p ios
   ```
   В меню — «Build Credentials» → «All: Set up all the required credentials to build your
   project»: регистрирует у Apple идентификатор `com.noxlabs.remember` (с пушами и входом через
   Apple), сертификат и профиль подписи. Затем «Push Notifications» → «Set up your project to use
   Push Notifications» — ключ APNs; без него сборка соберётся, но ни один пуш не придёт. Всё это
   хранит EAS, файлы ключей в репозиторий не кладутся.
4. Запись приложения в App Store Connect: Apps → «+» → New App — платформа iOS, Bundle ID
   `com.noxlabs.remember` (в списке он появится после шага 3), SKU любой, например `remember`, имя —
   любое свободное в App Store: на телефоне приложение всё равно подписано `Remember` из `app.json`.
5. Сборка в облаке EAS и коммит поднятого номера:
   ```sh
   eas build -p ios --profile testflight
   git commit -m "chore(mobile): номер сборки для TestFlight" app.json
   ```
6. Отправка в App Store Connect. `--profile testflight` берёт из `eas.json` номер приложения в App
   Store Connect (`ascAppId`) — без флага он не читается; `--latest` — последнюю сборку для
   магазина, только что собранную; вход в Apple спросит снова:
   ```sh
   eas submit -p ios --profile testflight --latest
   ```
   После загрузки Apple ещё несколько минут обрабатывает сборку, потом она видна во вкладке
   TestFlight. Вопроса про шифрование не будет — ответ уже в `app.json`
   (`ITSAppUsesNonExemptEncryption: false`).
7. Друзья — во внутреннюю группу тестировщиков. Сначала каждый становится пользователем команды:
   Users and Access → «+», его почта, доступ только к этому приложению; он принимает приглашение из
   письма. Затем приложение → TestFlight → «+» у Internal Testing → группа с галкой «Enable
   automatic distribution» (следующие сборки уйдут ей сами) → Invite Testers → отметить друзей.
   Им приходит письмо: ставят приложение TestFlight и уже из него — Remember. Кого нет в списке
   Invite Testers — тому смените роль в Users and Access.

**Что проверить с телефона после первой установки.** Вход по письму: на настоящий адрес приходит
письмо с шестью цифрами, после них открываются соглашение и ник — сервер снаружи жив и шлёт почту.
Кадры: новое воспоминание, в него пара фото и видео с телефона — загрузка доходит до конца, а через
минуту-другую у кадров появляются превью (их делает `montage`). Пуш: после входа приложение
спрашивает разрешение на уведомления — разрешить; позвать этот телефон в воспоминание со второго —
приходит пуш, тап по нему открывает загрузку в это воспоминание. Нет пуша — проверить ключ APNs из
шага 3 и разрешение в настройках телефона.

### Обновления по воздуху

Правка, не задевающая нативную часть, доезжает до телефонов без новой сборки — через EAS Update
(`expo-updates`). Сборка из профиля `testflight` слушает канал `dev` — канал дев-контура. Будущий
боевой профиль получит свой канал (`production`) и своё окружение EAS: обновление, выложенное в
`dev`, туда не попадает, и наоборот.

Выложить — из этой папки:

```sh
npm run update:dev -- --message "что поменялось"
```

Обновление собирается на этой машине, а не в облаке, поэтому `env` из `eas.json` к нему не
применяется. Скрипт сам вшивает тот же адрес сервера, что и профиль `testflight`, и не читает
локальный `.env` — иначе в телефоны уехал бы `localhost`. Меняется адрес дев-сервера — менять в
обоих местах.

На телефоне: при каждом холодном запуске приложение спрашивает сервер, и если есть новое — скачивает
и за несколько секунд перезапускается в него (`src/lib/updates.ts`). Приложение, висящее в фоне,
ничего не спрашивает: чтобы получить обновление, его смахивают и открывают снова.

**Что уходит по воздуху** — всё, что в JavaScript-бандле: экраны, логика, тексты, стили, кит,
картинки и шрифты, подключённые из кода, значения `EXPO_PUBLIC_*`.

**Что требует новой сборки в TestFlight** — всё нативное: поставить, убрать или обновить пакет с
нативным кодом (любой `expo-*`, `react-native-*`), переход на новый Expo SDK, правки `app.json`
(плагины, разрешения, иконка, сплэш, имя, схема, `infoPlist`) и `eas.json`.

Помнить этот список не нужно: решает версия среды (`runtimeVersion`) — отпечаток нативной части,
который считает сам Expo. `eas update` печатает её при выкладке; обновление достаётся только сборкам с той же
версией. Изменилась нативная часть — версия другая, старые сборки такое обновление просто не
увидят, и падения не будет: нужна новая сборка. Номер сборки и скрипты `package.json` в отпечаток
не входят (`fingerprint.config.js`), иначе каждая сборка была бы средой сама по себе.

Первая сборка, умеющая принимать обновления, — первая собранная после подключения `expo-updates`;
сборки до неё обновлений не получат никогда.

**Проверка с телефона.** Поставить свежую сборку из TestFlight, открыть. Выложить обновление с
заметной правкой, смахнуть приложение и открыть снова — через несколько секунд оно перезапускается
уже с правкой.

## Оболочка и токены

Дизайн-правда продукта — `design/spec.md` в корневом репозитории (макет «Афиша»: ночь основная,
день — подстановкой), её единственный перенос сюда — `src/theme/`: цвета, ритм, радиусы по роли,
высоты, вертикальные привязки доски, длительности и шкала типографики, имена и значения один в один
со спекой. Свои цвета и отступы экраны не заводят — берут отсюда.

- Шрифты — **Unbounded** 600/700 на заголовки и **Onest** 400…700 на всё остальное
  (`@expo-google-fonts/unbounded`, `@expo-google-fonts/onest`), оба с кириллицей. Каждое начертание
  — своё имя семейства (`Unbounded_700Bold`), а не семейство плюс `fontWeight`: одноначертательному
  загруженному шрифту Android иначе синтезирует вес вместо того, чтобы взять готовый. Шесть
  начертаний грузятся в `_layout.tsx` и держат сплэш вместе с проверкой сессии, а навигатор до
  них не рисуется вовсе: экран, нарисованный раньше шрифтов, так и остался бы в системном — его
  текст уже разложен и сам не перекладывается (TASK-380). Не загрузились — приложение открывается
  системным шрифтом, в логе строка `fonts fail to load`. Что файлы
  действительно несут кириллицу, проверяет `tests/theme/tokens.test.ts` — читает cmap самого ttf, а не
  метаданные пакета.
- Значки — **Lucide** (`lucide-react-native`), один набор на весь продукт; обводка не одна на всех,
  а тем толще, чем мельче знак (`strokeFor` в `src/kit/icon.tsx`, 1.5–2.1); свою толщину знак
  получает, только где макет называет её для места (`stroke`: плюс «Смонтировать» — 2.2).
  Треугольник «играть» у макета свой и меньше лукидовского в той же коробке: размер, на котором
  лукидовский ложится на него, даёт `playFor(коробка макета)` там же — 11 в 16 у «Послушать», 6 в 9
  у длительности в ленте (TASK-384), 9 в 13 и 8 в 12 у значка роликов на карточке (коробка остаётся,
  и слова в 6 от неё, TASK-398). Так же макет рисует по-своему, теснее лукидовских, ещё несколько
  знаков: сердце, молнию, лист и дом шаблонов, перо «править», «−» и «+» у длины. Их даёт
  `drawnAs(знак, доля)` — лукидовский знак целым размером в доле коробки, по центру её, той же
  толщины линии, что названа для места; доля — сколько охват рисунка макета (вширь + ввысь, по сетке
  24) от лукидовского. Готовые — `DRAWN` в `src/kit/icon.tsx`: место называет коробку и штрих макета,
  и чернила ложатся, куда у макета (сверяет `tests/kit/icon.test.tsx`). Телефон не своего размера у
  шаблона «TikTok» — свой рисунок макета (`smartphone-play`), в Lucide его нет. Он
  тянет за собой нативный `react-native-svg`: в Expo Go он есть, а **старый dev-билд надо
  пересобрать**.
- Градиенты — родные, `experimental_backgroundImage` со строкой CSS прямо из спеки (подвал донного
  слоя, затемнение обложки). Отдельной библиотеки под это нет; `experimental_` только в имени —
  RN 0.86 разбирает строку в JS и рисует её нативно.
- Кадры рисует **`expo-image`** (внутри `src/kit/tile.tsx`, наружу не торчит): родной `Image` не
  умеет `ph://…` — ссылку, которой iOS называет снимок в медиатеке, — и падает на ней красным
  экраном «No suitable image URL loader». `expo-image` спрашивает Photos напрямую, для видео
  отдаёт постер, и отдаёт уже уменьшенным под плитку. Модуль нативный: **старый dev-билд надо
  пересобрать**. Его манифест доливает в андроидную сборку `ACCESS_NETWORK_STATE` — разрешение
  обычного уровня, без диалога, но в списке на Play оно появится. Проявляется кадр **его же**
  `transition`, а не `Animated` поверх: нативный драйвер пишет прямо во вью, к которому привязан, а
  здесь это чужой класс вокруг нативного — значение доезжало до единицы в JS, картинка оставалась
  на нуле и появлялась только от постороннего перерендера. Плитки на экране выбора из-за этого были
  пустыми, пока по ним не ткнёшь.
- Свой трек для ролика выбирается системным выбором файлов — **`expo-document-picker`**
  (`audio/*`, только экран заказа). Модуль нативный и разрешений не просит, но **старый dev-билд
  надо пересобрать**.
- Музыку на том же шаге проигрывает **`expo-audio`** (`createAudioPlayer`, только экран заказа).
  Модуль нативный — **старый dev-билд надо пересобрать**. Его плагин в `app.json` стоит с
  выключенным микрофоном и фоновым воспроизведением (`microphonePermission: false`,
  `recordAudioAndroid: false`, `enableBackgroundPlayback: false`): приложение ничего не записывает и
  за пределами экрана заказа не звучит, а по умолчанию плагин просит `RECORD_AUDIO` и режим `audio`
  в фоне — и то и другое пришлось бы объяснять в сторах. Телефон живёт на беззвучном, поэтому перед
  каждым проигрыванием вызывается `setAudioModeAsync({ playsInSilentMode: true })` — без него iOS
  при выключенном звонке молчит.
- Родного хедера нет нигде (`headerShown: false`), фон навигатора — `ink` через `ThemeProvider`,
  так что шапку экран рисует сам.
- Приложение идёт за темой телефона, поэтому `userInterfaceStyle: "automatic"` в `app.json`: при
  `"dark"` система вообще не сказала бы, что телефон в светлом режиме, и светлая тема не включилась
  бы никогда. Настройка нативная — **ещё одна причина пересобрать dev-билд**.
- Продукт вертикальный, но нативного замка на это больше нет: в `app.json` стоит
  `orientation: "default"`, а портрет держит `src/lib/orientation.ts` — `lockPortrait()` из
  `_layout.tsx` при запуске и снятие замка на время двух просмотров во весь экран, кадра и ролика
  (`useTurnsWithPhone` — окно кадра `src/screens/memory/frame-viewer.tsx` и плеер ролика
  `src/screens/memory/film-player.tsx`). Окно кадра
  живёт ровно столько, сколько открыт кадр, поэтому флаг там простой `true`. Стоявший там `"portrait"` компилировался
  в Info.plist и андроидный манифест и был выше любого JS: `supportedOrientations` у обоих Modal
  не делал ничего, и открытый кадр не поворачивался вместе с телефоном (TASK-124). Замок ставит
  нативный `expo-screen-orientation`, и сама смена в `app.json` тоже нативная — **старый dev-билд
  надо пересобрать**.

### Тема — светлая и тёмная

Тем ровно две (`backlog/docs/doc-9`), и различает их только цвет: ритм, отступы, радиусы, шрифты и
длительности общие и о теме не знают. В `src/theme/` лежат оба набора: ночь нарисована в макете
целиком, день собран подстановкой по правилам раздела 2 спеки. У дня три места, где это не
подстановка, а другое решение, — карточку поднимает тень, а не обводка; затемнение поверх
фотографии остаётся тёмным; тень главной кнопки мягче. Каждая читаемая пара обоих наборов проверена
на контраст в `tests/theme/tokens.test.ts`, потому что на светлом `muted` идёт впритык (4.65 : 1).

- **Какая тема сейчас** — `src/theme/`: берётся от телефона (`Appearance` из React Native,
  нативного модуля для этого не нужно), меняется вместе с ним на ходу. `setTheme('dark' | 'light')`
  переопределяет систему, выбор лежит в `expo-secure-store` и переживает перезапуск. Устроено ровно
  как язык — модульная переменная и `useSyncExternalStore`, а не контекст.
- **Компонент рисует по актуальной теме**: свои стили он получает не импортом набора, а хуком —
  `const useStyles = themed(({ color }) => StyleSheet.create({ … }))`, дальше `useStyles()` в теле.
  Каждая тема собирается один раз и запоминается. Цвет, который нужен не в стиле, а в пропсе, —
  `useTheme()`.
- Кадры и медиа не перекрашиваются ни в одной теме: всё, что лежит **на фотографии**, а не на
  интерфейсе, собрано отдельно в `photo` — затемнение обложки, подложка метки, стекло просмотрщика,
  белый текст поверх. Оно одинаково в обеих темах.

```tsx

```

Значения берутся из `theme.ts`; своих цветов компоненты не заводят и жёстко тёмными не бывают —
кроме того, что лежит на стекле или на фотографии (см. ниже).

Четыре вещи, о которые спотыкается тот, кто их подключает:

- **Ни одного зашитого слова.** Всё видимое приходит пропсом: библиотека — это внешность, слова у
  экранов. Склонения («1 ролик» / «2 ролика») тоже приходят готовыми.
- **Текст — только `Text` из кита.** В CSS цвет наследуется от `body`, в RN — ни от чего, поэтому
  родной `Text` с одним лишь `type.body` даёт чёрное по угольному. Роль просите словом:
  `<Text role="title">`, цвет — `tone`. Вторичные роли (`meta`, `note`, `eyebrow`) сами берут
  `muted`; `faint` у слов, которые читают, не бывает — только у недоступного и у знаков вроде «@»
  (спека 10.1), и это держит `tests/kit/type-rules.test.ts`.
- **Движение гаснет по системной настройке.** Вращение, проявление кадра, подъём листа, сдвиг
  нажатия и полоса отправки слушают «уменьшить движение»; она спрашивается один раз на всё
  приложение в `src/kit/interaction.ts`. Оттуда же `hitSlop()` — им добирают до 44×44 всё, что
  нарисовано меньше (круглые 36 и 32), и `useFocusRing()` — кольцо фокуса, обязательное на каждом
  нажимаемом элементе.
- **Состояния — пропсом, а не второй деталью.** Кнопка не нажимается (`disabled`), ждёт сервер
  (`busy` плюс `busyLabel` — то же действие в продолженном времени), поле проверено или ошиблось
  (`state`), кадр отмечен или взят в ролик (`pick`: `accent` — отметка в ленте, в отправке и в
  выборе обложки, `spark` — «взят» в мастере).
- **Сетка кадров — две, и плитка знает, в какой стоит.** Лента воспоминания идёт во всю ширину,
  щель `FEED_GAP` (2), без скругления (`<Tile lane="feed">`); мастер и очередь — в полях 16, щель
  `GRID_GAP` (3), радиус 4 (по умолчанию). Одна деталь, две раскладки: ширину колонки экран считает
  из своей щели. Щель дня встаёт вместо щели 2, а не рядом с ней (спека, деталь 65): ряд над ней
  кончается на её верхнем крае, следующий начинается на нижнем — лента воспоминания, у которой
  ряды разведены `gap` списка, забирает у щели оба гаттера (`marginVertical: -FEED_GAP`).
- **Капсула стеклянной шапки — кнопка, только если есть куда вести.** Дали `onCapsule` — она
  кнопка (лента воспоминания, режим выбора); не дали — плашка-заголовок (`Upload`). Мёртвая кнопка,
  которая объявляет себя кнопкой и не отвечает на нажатие, хуже той, что ею не притворялась.
  **Шеврона нет ни в одной центральной капсуле** — ни в шапке ленты, ни в шапке просмотрщика
  (спека, раздел 1, правило 9): капсула — кнопка сама по себе, а стрелка только отнимает место у
  названия. Включить его нечем, и `chevron-down` в исходниках не встречается вовсе — это держит
  тест кита.
- **У строки один правый знак.** В строке участника это либо значок вклада, либо своя кнопка 44,
  либо крестик режима правки состава — они заменяют друг друга в слоте `status`, а не встают рядом.
- **Ряд с кнопкой в слова переносится.** Кнопка шириной в свои слова, чип и значок со словами
  («ОРГАНИЗАТОР», «2 ролика», «Взял 1 из 4») растут вместе с системным шрифтом, и ряд без переноса
  уводит их за край экрана — поэтому такой ряд всегда `flexWrap: 'wrap'`, в том числе ряд детали,
  куда кнопку или значок отдают слотом (`Banner`, `ActionBar` `above`, `RowContact`, `RowRejected`,
  `films` карточки воспоминания, `decision` карточки «Сейчас», `mark` строки этапа); держит перебор
  исходников `tests/kit/rows-wrap.test.ts` (TASK-365, TASK-375). Слова рядом с ней — `flexGrow: 1`,
  а не `flex: 1`: на крупном шрифте кнопка уходит под них, а не сжимает их по букве в строку (тот же
  перебор; пол `minWidth: '50%'` тоже годится). `flexShrink` к такому `flexGrow` не добавляют: Yoga
  единственному в ряду элементу, который и растёт, и сжимается, ставит основу 0 — это снова `flex: 1`,
  с переносом или без. И кнопка без `variant` — это `secondary`, а она во всю ширину: в ряду рядом
  со словами ей нужен `wide={false}`, иначе она сжимает их в ноль; кнопка во всю ширину стоит в ряду
  только с другими кнопками — это держит тот же перебор.
- **Слова, делящие строку, просят места сами** (`useWordRoom` в `src/kit/text.tsx`, TASK-375). Где
  перенос ряда не помогает — главная кнопка между круглыми 56 внизу ленты, имя плитки шаблона в
  половине сетки, имя обычной карточки рядом со значком роликов, слова пустого блока роликов рядом
  со стопкой кадров, имя готового ролика рядом с кругом «играть», мысль строки этапа рядом с
  решением, — деталь стоит как в макете, пока ни одно её слово не порвалось, и переходит в
  просторный вид, как только порвалось: круглые встают рядом над кнопкой во всю ширину, плитка берёт
  ряд целиком, значок и решение уходят под слова, стопка и круг — над словами. Порванное слово
  сообщает телефон: каждый `Text` кита внутри `WordRoom.Provider`
  проверяет свои строки из `onTextLayout` (`brokeWord`: на стыке двух строк нет ни пробела, ни дефиса,
  ни тире). Решение держится до смены ступени шрифта или ширины окна — в просторном виде слова целы,
  и назад по ним не прыгает. Просторный вид задаётся шириной, а не `flexBasis`: основу, однажды
  вычисленную для узла, Yoga больше не пересчитывает, и новая до телефона не доходит. По той же
  причине коробка, которую два вида меняют стилем, — новый узел в каждом виде (`key={way}` из
  `useWordRoom`): `flex: 1` задаёт основу, и коробка, вернувшаяся из просторного вида (смена шрифта
  при открытом приложении), держала ширину во всю строку — значок роликов карточки стоял под именем,
  рядом с которым ему было место (TASK-406). Вещи в равных
  долях ряда — «Сохранить» и «Поделиться» под готовым роликом, три плитки-числа, плитки дней в
  фильтре — стоят в `Shares` (`src/kit/bits.tsx`): рядом, как в макете, пока ни одно слово в них не
  порвалось, и друг под другом во всю ширину, как только порвалось (TASK-400). Держит
  `tests/kit/word-room.test.tsx`.
- **Слово не рвётся нигде — последнее средство в самом `Text`** (TASK-400). Слово, которое порвалось
  и там, где детали больше некуда перестроиться (`room()` отвечает, сделала ли деталь место), или
  вне такой детали, растёт не дальше, чем его строка держит целиком: `Text` находит порванное слово
  по строкам телефона (`wholeAt` — ширина строки к ширине слова) и дальше рисуется уже выросшим
  размером (`fontSize` и `lineHeight`, умноженные на найденное) без дальнейшего роста, но не меньше
  размера макета (размером, а не потолком — см. следующий пункт). Так
  всегда делает широкий Unbounded — всё, что растёт (`WIDE`): потолки `HEADING_MOST` меряны на 375,
  а на 360 Android и на 320 режима увеличения строка уже; имя воспоминания и имя человека не
  измерить вовсе. Onest — только по просьбе (`fit`): подпись «Проявляем…» на плитке, адрес почты
  и «@ник» — слова без пробелов. Остальной текст строки не спрашивает — это второй обсчёт каждого
  абзаца. **Порванного слова не видно ни в одном кадре** (TASK-407): строки из `onTextLayout`
  приходят после кадра, который их нарисовал, и на холодном старте «Проявля / ем…» стояло кадр.
  Поэтому выросший текст (ступень крупнее обычной), который спрашивает, проверяется раньше: рядом с
  ним невидимая копия тех же слов — по куску на строку, кусок не рвётся строкой (слова, слово с
  дефисом или тире — после него, `piecesOf`), в коробке шире любого слова, — и в `useLayoutEffect`,
  где новая архитектура уже знает раскладку этого коммита (`measure` отвечает сразу), самый широкий
  кусок сверяется с шириной коробки текста. Шире — деталь делает место (`room()`) или слова
  ставятся на столько меньше, сколько коробка держит (минус 2 % на округление), и всё это до
  монтирования: React перерисовывает синхронно, а экран монтируется в конце задачи JS. Строки из
  `onTextLayout` у такого текста только повод спросить раскладку заново — ими не решают: строки
  раскладки, уже поправленной, порванные, а ответ по ним лишний раз уменьшал слова. Цена: на ступени
  крупнее обычной у каждого спрашивающего текста одна невидимая копия (ещё один абзац в замере) и два
  синхронных чтения раскладки на рендер; лишних перерисовок нет — та, что ставит слова меньше, была
  и раньше, только после кадра. На iPhone SE при AX5 копий: лента 8 (из 38 текстов), главный 10
  (из 23), готовый ролик 9 (из 23), создание с календарём 1 (из 48). На обычной ступени копии нет
  вовсе, и раскладка та же. Держит `tests/kit/first-frame.test.tsx`.
- **Рост шрифта — размером, а не потолком** (TASK-406). Ни один текст кита не растёт силами
  платформы: `Text` рисует слова уже выросшими — `fontSize` и `lineHeight` роли, умноженные на
  ступень системного шрифта, но не дальше потолка роли или клетки, — с `allowFontScaling={false}`.
  Причин две. Кэш замеров текста React Native (`TextMeasureCache.h`, ключ «по раскладке») потолок
  (`maxFontSizeMultiplier`) не учитывает: пониженный потолок у уже нарисованного текста рисовался
  мельче в коробке прежней высоты, а строки для `onTextLayout` приходили прежние. И смена системного
  шрифта при открытом приложении: платформа перемеряет свои узлы текста, а следующий коммит React
  подставляет обратно свои — со строкой, собранной при прежней ступени, и прежним замером Yoga; на
  iPhone SE после AX5 → L плитки и этапы готового ролика стояли высокими с мелкими словами до
  перезапуска. Размер в пропсах меняется с каждой ступенью, и React сам ставит новый узел каждому
  тексту. Для этого каждый `Text` подписан на размеры окна (`useWindowDimensions`): подписка — один
  слушатель на текст (лента — 38 текстов, создание с календарём — 48, главный — 23), перерисовка —
  только при смене ширины окна или ступени шрифта (AX5 → L при открытом приложении: на ленте 101

неделей одной лентой (`ribbonOf`), а не куском под каждым днём: на стыке двух кусков iOS рисовал

поля-кнопки даты (`FieldShell` + системный `DateTimePicker`) больше нет — ни на экране, ни в ките,

Лист снизу — это `Sheet` (`src/kit/sheet.tsx`): подложка, ручка 40×4, подъём, закрытие по тапу вне,
заголовок, тело и неподвижный блок кнопок внизу. Обводка у листа только сверху, 1 (спека 7.1,
деталь 7): по бокам её нет, поэтому содержимое 358 от x 16, как колонка экрана, а ручка — в 13 от
края. Тело прокручивается у любого листа, как только не
влезло в девять десятых окна, — флага для этого нет, и новый лист забыть о прокрутке не может
(TASK-358); ручка, заголовок и кнопки при этом стоят. Если же они сами с одной строкой тела не
влезают (самый мелкий телефон на самом крупном системном шрифте), под ручкой прокручивается весь
лист целиком — иначе кнопки оказались бы за краем экрана. Решает это `pinnable` по размерам, которые
лист мерит у себя на экране; строка тела в нём не выше ×2 (`TYPE_MOST`) — выше слова тела не растут;
на обычном шрифте такого не бывает. Абзац в 8 под заголовком (`SheetRejected`, `SheetAskAll`) —
`lead`, первые слова тела, а не часть заголовка: он прокручивается с телом, а стоят, как в спеке,
только ручка, заголовок и кнопки. Стоявший вместе с заголовком абзац оставлял строкам «Вернуть» на
iPhone SE при AX щель в 139 (TASK-401). Клавиатуре лист уступает
(`KeyboardAvoidingView`) только поднявшись (TASK-386): подъём идёт на нативном драйвере, и до его конца
React держит у листа начальные значения — прозрачный и на 24 ниже; сдвиг под клавиатуру — это
layout-анимация, и та, что застала лист на подъёме, проигрывала его из этих значений и в них же
оставляла. Поле с автофокусом («Новый лейбл») давало затемнение и клавиатуру без листа. Что
клавиатура сделала за время подъёма, лист помнит и уступает ей разом, когда поднялся. Что каждый
лист приложения — этот `Sheet`, а не свой `Modal`, держит тест кита. Пять видов листа из спеки —
это пять разных `footer`, а не пять флагов. Всё в листе — одна колонка с одной щелью, как в макете: ручка, блоки, распорка,
кнопки (между кнопками 8). Щель — `rhythm`: по умолчанию 18 (подтверждения и вопросы), `tuning` — 20
(сортировка и фильтры), `list` — 14 (сведения о кадре, лейблы, файл журнала); чисел экраны не
передают. Лист по умолчанию высотой в то, что держит; `height` — высота листа из спеки (раздел 4)
как пол, а не потолок: остаток уходит в распорку над кнопками, а лишнее содержимое лист вмещает,
ничего не сжимая (спека 10.10 — у трёх листов макета ручка сжата в ноль). Высоты — в `height`
темы: сортировка 381, фильтры 560, а `ConfirmSheet` берёт свою по тому, о чём спрашивает, — кадр и
лейбл 380, человек 420, воспоминание 434. `ConfirmSheet` спрашивает необратимое вместо системного
`Alert.alert`: он называет цену цифрой до нажатия. Строка под вопросом (`meta`) стоит и без
картинки рядом: у кадра без миниатюры она всё равно говорит, кто снял, а у пачки — почему уходит
меньше, чем отмечено.

Экран прокручивается там же, где лист, — в доске (`Board`, `src/kit/bars.tsx`), на которой стоит
каждый экран (TASK-372). Экран отдаёт ей куски, а не колонку: `bar` — шапку и то, что прибито под
ней (поле поиска контактов, чипы журнала этапа), `heading` — заголовок под шапкой (заголовок шага
мастера, а с ним строка счёта на шаге кадров), `footer` — донный слой и строку над ним, детей —
тело, `body` — стиль колонки тела (поля, щели). Тело прокручивается
всегда, как только не влезло, — своего `ScrollView` у экрана нет, и новый экран забыть о прокрутке
не может; шапка и подвал при этом стоят. Если же они сами с одной строкой тела не влезают в окно, вся
доска прокручивается целиком — то же правило, что у листа; строка тела и здесь не выше ×2. Подвал
держит высота окна, а не место над
ним: его забирает клавиатура, и поле в подвале, переехавшее в прокрутку, рисуется заново — клавиатура
уходит вместе с ним. Верх держит место над подвалом, и уступает он по частям (TASK-381, TASK-401).
Сначала заголовок: если клавиатура оставила меньше, чем шапке, заголовку и полю длинного текста в
три строки под ними (`areaSight` в `src/kit/field.tsx` — три строки на той ступени, до которой они
растут, и края поля), заголовок уходит в голову прокрутки, а строка шапки с «Назад» и «Отмена» стоит
(на iPhone SE заголовок шага «История» с поднятой клавиатурой уходит так с обычной ступени L и
крупнее; на 390 × 844 на обычном шрифте — нет). Потом шапка — если места меньше, чем ей и строке тела. Тело
остаётся на экране там, где было, ушедшее — прокрутка вверх; клавиатура убрана — верх стоит снова.
Поле тела, в которое пишут, доска при этом докручивает в то, что оставила клавиатура: целиком, а
выше оставшегося — от верха (`focusedField` в `src/kit/field.tsx`). Докручивает дважды: когда
клавиатура забрала место и когда она поднялась (`keyboardDidShow`) — фокус поля и место клавиатуры
приходят в JS разными дорогами, и место часто первым: доска тогда ещё не знала поля, и на обычном
шрифте поле истории стояло, где стояло, одной-двумя строками над «Дальше» (TASK-401). Длинный текст
(`TextArea`) прокручивается внутри себя и держит каретку в своей рамке, поэтому он не выше того, что
доска показывает от тела (`AreaRoom`): целиком на экране, каретка не за «Дальше» и не за клавиатурой;
без клавиатуры на 390 × 844 телу хватает места на все его 280. Тело при этом никуда не переезжает, и поле в нём не рисуется заново; шапка
со своим полем (поиск контактов — каждое поле кита сообщает о себе шапке через `useFieldInBar`) не
уходит никогда. Тело, которое само список (`FlatList`: главная, шаг кадров, журнал этапа, лента
«Ваших кадров»), экран рисует сам в `list` — доска отдаёт ему шапку, заголовок и подвал, чтобы
поставить их в голову и хвост списка,
когда стоять им негде; дети доски тогда — то, что висит поверх списка. В теле `flex: 1` у блока с
содержимым не ставят — только `flexGrow`: сжатый до нуля блок вылезает из прокрутки, а не
прокручивается. Клавиатуре уступает тоже доска, одна за все экраны: на iOS она поднимает подвал с
кнопкой над клавиатурой (`KeyboardAvoidingView`), Android делает это сам; `automaticallyAdjustKeyboardInsets`
рядом не ставится — вместе они сдвигают дважды. Если клавиатура оставила меньше места, чем нужно
тому, что стоять обязано (подвалу, шапке со своим полем), уступает верх, а не кнопка: доска стоит
на нижнем крае (`justifyContent: 'flex-end'`). Убирается клавиатура обычными жестами, тоже одним
местом на все экраны и листы (TASK-377, `src/kit/interaction.ts`): тап или протяжка, начатые на
всём, что не поле и не кнопка, — фоне, словах, подвале вокруг поля, теле, которому нечего
прокручивать (`DISMISS_KEYBOARD`), и протяжка прокручиваемого тела (`KEYBOARD_SCROLL`:
`keyboardDismissMode="on-drag"`, а тап по кнопке при поднятой клавиатуре нажимает кнопку). Касание,
начатое на кнопке или поле, остаётся им, даже если палец дрогнул: доска и лист спрашивают о касании
только в его начале, а не на каждом движении — иначе дрожь пальца отдавала им нажатие, и тап по
«Сохранить» над клавиатурой или по соседнему полю только убирал клавиатуру. Свои
`keyboardShouldPersistTaps` экраны не пишут — это держит `tests/routes/scroll.test.ts`. Шаг мастера — та же доска
(`WizardStep` отдаёт ей шапку мастера `WizardBar` — строку и шкалу, — заголовок шага `WizardHeading`
и донный слой; шаг — тело или `list`), и заголовок шага над полем истории или пожелания уходит под
клавиатурой в прокрутку по тому же правилу доски, без своего кода у мастера. Клавиатура убирается и
там, где поле истории заняло всё тело: касанием или протяжкой по строке шапки («Шаг 2 из 4»), по
подвалу под «Дальше» и по краю тела вокруг поля.
Вне доски два маршрута, и оба названы в `tests/routes/scroll.test.ts`: `+not-found` (перенаправление)
и лента воспоминания — список во весь экран, над которым висят стекло и донный слой. Лента
отступает от них по тому, какими они вышли, а не по макету: подвал с кнопкой, перенесённой на
крупном шрифте, выше 190, и последний ряд кадров иначе остаётся под ним; строка «воспоминание не
прочиталось» висит под стеклом, пока есть место, и уезжает в голову ленты, когда нет.

Клетки, ширину которых задаёт макет, — день календаря, готовая длина на ползунке — растут на крупном
шрифте вниз, а не вширь: `fitCell` в `src/kit/text.tsx` держит цифры в клетке
(`maxFontSizeMultiplier` по измеренной ширине) и растит клетку под них, не ниже 44. Ширина известна
только после раскладки, и потолок ложится на уже нарисованные цифры — поэтому `Text` рисует его
размером, а не потолком: иначе кэш замеров React Native оставлял цифрам коробку прежнего роста
(ревью TASK-400). На обычном шрифте
клетка та, что в макете. Неделя уже семи пальцев (iPhone SE в режиме увеличения экрана, 320: неделя
262, колонка 37) дать дню 44 в ширину не может, а вбок спека не прокручивает ничего (правило 5), —
поэтому день там — седьмая доля ряда без зазоров и нахлёстов, а в высоту 44 на любой ступени шрифта
вместо 40 макета, и кружок дня не шире колонки (TASK-375). Касание в любом месте недели попадает в
ближайший к нему день; где колонка держит 44, день прежний. Буквы недели держит в колонке та же
`fitCell`, и мерка у них — самые широкие буквы обоих языков, английское «MON» (2.59 em против 1.59 у
«ПН»): мерка по одному «ПН» рвала английские в «MO / N» (TASK-404). Концы ползунка под дорожкой
стоят в строку с зазором 12, а когда так не помещаются — правый уходит строкой ниже, по-прежнему у
правого края. Обе мерки сверяет по файлу шрифта `tests/kit/large-type-cells.test.tsx`.

#### Истории

Отдельного Storybook нет и не будет (в браузере продукт не проверяется, см. «Чего здесь нет»).
История каждого вида и состояния — это тест рядом с деталью: `src/kit/*.test.tsx` рендерит её через
`react-native-web` и читает разметку. `src/kit/story.tsx` — вся оснастка: `story()` рисует одно
состояние, `allDifferent()` требует, чтобы перечисленные состояния отличались друг от друга (деталь,
неотличимая от соседней, — это не состояние). Нативные модули подменены один раз на весь прогон в
`vitest.setup.ts`, а не в каждом файле. Значок Lucide там — голый `<svg>` со своим именем
(`data-glyph="Unlink"`), один и тот же на каждый импорт: какой знак нарисован, видно и в разметке,
и сравнением `props.icon`.

Той же оснасткой проверяется поверхность экрана, которой нечего держать, кроме переданного, —
три листа воспоминания (`tests/screens/memory/frames-sheets.test.tsx`: «Сведения о кадре» — читаем, не
прочли, весь целиком; фильтры — ничего не выбрано, выбрано, под условия не попал никто, ряд лейблов
с личным и общим и воспоминание без лейблов вовсе, плитки при одном, двух, трёх и многих днях, лица
при одном, шести, семи и двенадцати людях; сортировка
— порядок и группы, тумблера дат нет) и листы лейблов (`tests/screens/memory/label-sheets.test.tsx`: пусто, две
группы, режим правки, отказ сервера). И то, что в светлой теме каждый выглядит иначе, чем в
тёмной, — обе рисуются через `<ThemePin>`, так что проверка на две темы не требует переключать тему
приложения. Так же и устроено разделение: лист рисует то, что ему передали, а запросы и состояние
держит обёртка рядом (`LabelSheets`) — иначе ни одно состояние листа не попало бы в историю. Экраны
целиком так не рендерятся: у них роутер, запросы и своё состояние, и про них тесты читают исходник
(`src/*-screens.test.ts`) — то, что можно сказать про исходник (что где стоит и чего нет), — а поведение
проверяется потоками: экран идёт через `react-test-renderer` с настоящим клиентом api и поддельным
`fetch`, тест нажимает то, что нажал бы палец, и читает, что нарисовано и что ушло в сеть. Так идут
лейблы (`tests/screens/memory/label-sheets-flow.test.tsx`, `tests/screens/memory/frames-labels-flow.test.tsx`) и экраны
вехи «Афиша 2»: лента (`tests/screens/memory/frames-feed-flow.test.tsx` — выбор, удаление пачкой, скачать и
поделиться, сортировка и фильтры, стержень дат, перечитывание в фоне; смена «Дат между днями» в
аккаунте при двух открытых лентах — `frames-dates-flow.test.tsx`), «Ролики»
(`films-flow.test.tsx`), просмотр кадра (`frame-viewer-flow.test.tsx`), настройки, правка и создание
воспоминания (`settings-flow`, `edit-flow`, `create-flow`), «Добавить кадры» и её очередь (`upload-flow`), главный экран
(`home-flow`), аккаунт (`profile-flow`), лист приглашения (`memory/invite-sheet-flow`); четыре экрана журнала монтажа (сборка, журнал этапа, ролик, лента) идут ещё и на записанных
ответах api (`tests/recorded-api/`). Оснастка: `tests/helpers/renderer.ts`
(`mountsTrees()` и `mounted(tree)` — дерево снимается после теста, иначе экран, читающий сам себя по
таймеру, читает через поддельный сервер следующего теста), `tests/helpers/api.ts` (поддельный сервер по
маршрутам и записи), `tests/helpers/gesture.ts` (палец для `PanResponder`: ползунок, стержень, свайп по
кадру), `tests/helpers/labels.ts` (записи лейблов). Нативные модули, которых в node нет, тест подменяет у
себя (`expo-video`, `expo-media-library/legacy`, `@/downloads`) — общие лежат в `vitest.setup.ts`.
`react-test-renderer` в React 19 помечен устаревшим, но работает; он пришёл вместе с версией `react`
(обе зафиксированы). Ширина окна под node — ноль на ноль: тест, где что-то меряется от неё
(плитки, стержень), подставляет её сам.

Что видно в такой разметке, а что нет: стиль, собранный на рендере (тернарник, размер из пропса),
пишется в `style="…"` с цветами; стиль из `StyleSheet.create` — а это и всё, что возвращает
`themed()`, — сворачивается в класс-хеш. Поэтому цвет с двумя ответами читается прямо только там,
где он собран на рендере; форма и цвет из готового листа — сравнением одного состояния с другим
или по классу: `rule('gap:10px')` из `tests/helpers/css.ts` называет класс, в который свернулось
объявление.
Состояние доступности (`accessibilityState`) в статическую разметку `react-native-web` не попадает
вовсе: роль и подпись проверяются, «отмечено» — сравнением.

Шесть проверок шрифтов на кириллицу (`tests/theme/tokens.test.ts`) и замер слов по файлу шрифта
(`tests/helpers/font.ts`) находят ttf через резолвер модулей, а не по пути от рабочей папки: в отдельной рабочей копии (worktree) они идут по ближайшему `node_modules`
выше по дереву и зелёные, пока пакеты стоят где-нибудь там.

## Язык

Языка два — русский и английский, третьего не будет (`backlog/docs/doc-8`). Оба набора написаны
руками: английский не перевод русского, русский не перевод английского.

- **Слова** — `src/strings/`: один ключ, два набора. Форму задаёт `en`, `ru` обязан её заполнить,
  поэтому ключ с одним набором роняет `npm run typecheck`, а не показывает английское слово посреди
  русского экрана. Русские числительные считаются в трёх формах (`1 кадр`, `2 кадра`, `5 кадров`)
  своей функцией: `Intl.PluralRules` есть в Hermes не везде.
- **Язык** — `src/lib/language.ts`: берётся от телефона (`expo-localization`), незнакомый язык телефона
  даёт английский. Переключается `setLanguage('ru' | 'en')`, выбор лежит в `expo-secure-store`
  (не секрет — просто хранилище, которое в приложении уже есть) и переживает перезапуск.
  Значение одно на всё приложение, поэтому это модульная переменная, а не контекст: `currentLanguage()`
  спрашивают из любой функции, компоненты берут `useLanguage()` / `useStrings()` и сами
  перерисовываются на переключении. Никакого i18n-фреймворка под этим нет — словарь и резолвер, как
  `theme.ts` для дизайна.
- **Даты** идут по языку приложения, а не по системной локали телефона: название месяца в
  `src/lib/dates.ts` спрашивается у `currentLanguage()`. Раньше там стоял `undefined`, а это для
  форматтера значит «локаль устройства» — из-за него на телефоне с русской локалью посреди
  английских подписей стояло русское число. Год пишется, только если он не текущий (спека 9,
  TASK-394): «3 октября», «12–14 сентября», «28 августа — 2 сентября», но «3 октября 2025» и
  «31 декабря 2025 — 1 января 2026» — одно правило у `formatDay` и `formatEventDates` для карточек,
  капсулы ленты, настроек, обложки и роликов. «Сегодня» у обоих — последний аргумент `now`; тест,
  который читает дату с экрана, ставит его через `thisYear2026()` из `tests/helpers/clock.ts`, иначе
  он сломается первого января.

`expo-localization` — нативный модуль: в Expo Go он есть, **старый dev-билд надо пересобрать**.
То же с `expo-location` (название места в листе «Сведения о кадре»): в билде без него экран
воспоминания не откроется — модуль ищется при импорте.
Поэтому же любой тест, который тянет `@/dates`, `@/language`, `@/theme` или любую деталь
библиотеки, подменяет `expo-localization` и `expo-secure-store` — в node их импорт падает на
`__DEV__`. Подмена общая и лежит в `vitest.setup.ts`, отдельно в файле теста её писать не нужно.

Экраны словарь ещё не читают (это отдельная задача вехи m-13), в `strings.ts` пока то, что
приложение говорит вне экранов: ошибки, состояния и слова, которые повторяются везде.

## Экраны

Навигация — `expo-router` (файловая маршрутизация, `src/app/`), корневой layout — `Stack` с гейтом.

Само воспоминание — **один экран без вкладок** (спека, раздел 8, `MemoryFrames`): лента кадров идёт

- **`index` — Remember** (`src/app/index.tsx`) — главный экран: список воспоминаний, где аккаунт

  обычную карточку с пунктирной плёнкой. Выбранная организатором обложка (`cover_thumbnail_url`)
  — такая же фотография: она рисуется во всю крупную карточку вместо мозаики, в обычной встаёт
  первой в полосе, и её одной хватает, чтобы карточка была крупной. Не выбрал обложку — карточка
  ровно такая, какой была. Кадры под обложкой карточка берёт из широкой случайной выборки по всему
  воспоминанию (`card_thumbnail_urls`, до двенадцати), а для api старше этого поля — из последних
  (`recent_thumbnail_urls`); лицо из них она перерисовывает раз в пять часов (TASK-544) и только из
  тех ссылок, что уже принёс список, — по таймеру ничего не запрашивается, а выбранная обложка не
  двигается. Полоса «сколько уже скинули кадры» считана самим списком
  (`member_count` / `contributed_member_count`), запроса на карточку нет. Перезапрашивается на
  каждый фокус, поэтому возврат с `create` показывает новое воспоминание сам. Карточка открывает
  воспоминание на «Кадрах». Связь — полоса в верху тела, а не замена списку: сорвавшийся перезапрос
  оставляет список на месте и вешает над ним баннер с крестиком, вернувшаяся связь показывает
  `spark`-баннер, который уходит сам через `duration.hold`. Своей библиотеки состояний связи нет:
  всё это — три ответа одного `listMemories`.
- **`create` — New memory** (`src/app/create.tsx`) — название и «когда это было»: календарь кита
  прямо в форме, первый тап — день, второй — конец диапазона, третий начинает заново; тап раньше
  начала считается поправкой первого. Над ним строка выбранного («12–14 сентября · 3 дня»; один
  день — без длины) и четыре быстрых дня (`Сегодня · Вчера · Выходные · Неделя`), под ним — одна
  подпись. Тумблера «больше дня» и системного выбора даты больше нет. Показанный месяц — своё
  состояние, поэтому листание стрелками не трогает выбранное, а завтрашний день не выбирается
  вовсе (`max`). Уходит в `POST /memories` началом и концом **local** суток — `toISOString()`
  даёт RFC 3339 со смещением, которого требует `api`; один день конца не шлёт вовсе.
- **`memory/[id]` — Memory** (`src/app/memory/[id].tsx`) — само воспоминание, один экран без
  вкладок. Сверху стеклянная шапка (`MemoryHead` в `src/screens/memory/head.tsx` на `GlassBar` кита): слева
  «назад» (без стека — `replace` на список), по центру капсула с именем и «даты · N человек», справа
  круглая «Выбрать». Капсула ведёт в настройки воспоминания (`memory/[id]/settings`), в режиме
  выбора та же капсула берёт все кадры; шеврона в ней нет ни там, ни там. Снизу
  донный слой на 190 с тремя кнопками. Ни шапка, ни подвал не занимают места в ленте: оба висят над
  ней абсолютом, каждый со своим градиентом.
  - **Кадры** (`src/screens/memory/frames.tsx`) — что сложили участники (`GET /memories/:id/media`): сетка
    деривативов по три в ряд по умолчанию **во всю ширину экрана**, щель `FEED_GAP` (2), без полей и
    без скруглений (`<Tile lane="feed">`) — её видит любой участник, включая `viewer`. Плотность
    3 / 5 / 7 / 1 задаётся щипком прямо в ленте (TASK-545, спека 10.14); последний шаг — один кадр
    во всю ширину, щель 0, дни читаются со стержня слева (`MemorySingle`).
    **По умолчанию лента — сплошная стена без единой щели**, а даты читаются со стержня у левого
    края: тонкая линия с пилюлями на швах между рядами, где начинается день (`DateSpine` кита,
    деталь 66); метка идёт от линии вправо — точка на линии, штрих, пилюля с датой. Левый край, а не
    правый: стержень стоит там, где палец, и дату под ладонью не прочесть. Он виден, только пока ленту
    ведут пальцем, гаснет через секунду после остановки, и его можно тянуть — палец по стержню
    переставляет ленту. Ленты короче экрана — стержня нет вовсе.
    Метки стоят в координатах самой ленты и едут вместе с ней нативным `translateY` от `onScroll`
    (`Animated.FlatList`), а не перерисовкой экрана на каждый кадр; где они стоят, считает
    `dateMarks` в `src/lib/frames.ts` из высоты блока «Ролики» (её меряет `onLayout`) и шага ряда.
    «Даты между днями» меняет это на узкую щель 20 px с «13 сентября, суббота» между днями — и тогда
    стержня нет (`MemoryScrub` / `MemoryDated` спеки). Это **настройка аккаунта**, одна на все
    воспоминания и все телефоны человека, а не сортировка ленты: приходит в профиле
    (`dates_between_days`), лента читает её из `useAuth().datesBetweenDays`, а меняет
    `setDatesBetweenDays` — сразу во всех открытых лентах, с откатом к тому, что держит api, если он
    отказал. На «Добавить кадры» и «Мои кадры» не влияет: там даты между днями всегда.
    Группы (`groupFrames` в `src/lib/frames.ts`) — «Не собирать · По людям · По типу»: **дни группой не
    считаются**, дата — это подпись; при группировке по людям или типу настройке дат добавить нечего.
    В щели по людям — аватар, имя и число кадров (`FramesByPeople`), в режиме выбора
    вся щель становится кнопкой «Выбрать все N» по своей группе: кружок в ней горит, когда группа
    взята целиком, повторный тап снимает только её (`toggleDay` в `src/lib/frames.ts`). Что показать (кто принёс, тип,
    день) и в каком порядке — два листа снизу, `src/screens/memory/frames-sheets.tsx`: фильтр остаётся
    черновиком, пока его не применили кнопкой с числом («Показать 486 кадров»; ничего не выбрано —
    «Показать все», под отбор не попал никто — кнопка недоступна и говорит это словами), «Сбросить»
    стоит маленькой кнопкой у заголовка, а сортировка применяется сразу. «Кто принёс» — одни лица
    без подписей (`FaceToggle` и `FaceRow` кита): пока никто не выбран, все лица в полную силу;
    выбран хоть один — выбранные в светлом кольце с галочкой, остальные приглушены: приглушение
    значит «исключён», и решает это ряд (`FaceRow`), а не лист. Не влезли в ряд — переносятся на
    следующий, столбцы держатся по первому ряду (`faceGap`), прокрутки и «+N» нет. «День» — плитки
    (`DayTile`): число, день недели, полоска объёма и число кадров. Воспоминание одного дня раздела
    «День» не имеет вовсе — выбирать не из чего (TASK-542); при двух днях и больше плиток столько,
    сколько дней, но не больше трёх, и они делят ряд поровну;
    при четырёх днях и больше это три самых полных по числу кадров, в порядке дат (`dayTiles`), а
    остальные выбираются календарём — круглая кнопка в шапке блока рядом с «Все дни», и открывает он
    календарь кита прямо в листе. Выбран день, у которого плитки нет, — лист открывается с уже
    раскрытым календарём, отметка на этом дне: иначе на листе ничего не сказало бы, чем сужена лента. Счёт в плитке — кадры дня по всему воспоминанию, полоска — байты
    файлов дня к самому тяжёлому дню (`size_bytes` приходит у каждой записи), а если размер не
    сложился ни у одного дня — кадры к самому полному (`filterDays`). Третьим разделом, между «Тип»
    и «День», стоят **лейблы**: чип с квадратом цвета, названием и счётом кадров, у личного — замок (`listLabels`
    читается отдельно от галереи и ещё раз при закрытии листов лейблов, так что заведённый,
    переименованный, удалённый или наполненный лейбл виден без перезапуска; не прочитались — раздела
    просто нет). Выбрать можно несколько — останутся кадры хотя бы в одном из них, отбор идёт на
    телефоне по `label_ids` кадра (`framesMatching`), а удалённый лейбл — здесь или кем-то другим —
    уходит и из фильтра (`keepLabels`), иначе лента сузилась бы до коробки, которой больше нет. Обе
    круглые кнопки подвала носят искру, когда их настройка ушла от умолчания (`filtering`, `arranged`);
    даты аккаунта искру сортировки не зажигают.
    Оригиналы отсюда не тянутся вообще. Медиа, которому воркер ещё (или уже никогда) не сделал
    превью, — плитка с подписью вместо картинки. Тап открывает кадр во весь экран
    (`src/screens/memory/frame-viewer.tsx`, экраны `Viewer` и `ViewerVideo` спеки): всё управление — три
    стекла сверху, «Закрыть» · капсула «когда» над «время · автор» · «⋯», а снизу только лента
    миниатюр для листания (`Filmstrip` кита) — она всегда стоит по центру открытого кадра и свайпом
    по ней листает кадры (TASK-540). Ряда круглых кнопок под лентой больше нет: что с
    кадром сделать — в стеклянном меню, которое выпадает из «⋯» (`ActionMenu` кита, деталь 9):
    «Поделиться», «Сохранить на телефон» и красное «Удалить из воспоминания», которого у того, кому
    нельзя, просто нет. Кнопка под открытым меню остаётся подсвеченной (`photo.held`).
    Видео играет 720p-превью
    прогрессивно (`expo-video`, `useVideoPlayer`) прямо по подписанной ссылке и носит свою дорожку с
    таймкодом, звуком и паузой — нативный транспорт выключен.
    Тап по самому кадру убирает всё это хозяйство и оставляет только кадр: стекла, затемнения и лента
    уходят вместе, а второй тап возвращает их (TASK-476, из doc-12). Прятавшийся интерфейс
    возвращается и сам собой по любому движению вперёд — по смаху по кадру и по шагу через `walk`, —
    так что заперться без пути назад нельзя. Смах по кадру ведёт и сам кадр за пальцем (TASK-540):
    в окне нарисованы три кадра в ряд — открытый посередине и двое соседей по бокам, — и палец
    двигает весь ряд, так что смахиваемый кадр уходит за край экрана, а следующий въезжает на его
    место; соседи нарисованы той же картинкой, что и лента, — своей миниатюрой, которая на телефоне
    уже лежит, а не большой копией. Отпустили дальше порога — ряд доезжает до соседа и открывает его;
    не дотянули — возвращается. За краями ленты соседа нет, и ряд туда не едет вовсе. Видео на тап не прячет ничего, а играет и встаёт на
    паузу: «Пауза» 72 посреди кадра остаётся на месте и в этом состоянии тоже. Тап не отнимает у
    свайпа его жест (палец берётся один раз, `PanResponder` тот же и построен один), и экранному
    чтению он доступен под тем же действием `activate`, что и палец.
    Капсула поднимает сведения о кадре — не лист, а экран под кадром (`FrameInfo`, TASK-478):
    кадр остаётся наверху и ужимается в верхние 289 px (на повороте — в свою долю окна,
    `frameInfoRoom`), панель сведений приезжает снизу и листается, лента кадров на это время уходит,
    потому что панели она не касается. Приезжает она движением, а не рывком (TASK-540, спека 10.14.3):
    260 мс вверх и 200 вниз, и кадр ужимается тем же движением — комната кадра, его коробка и ход
    панели читают одно значение, так что врозь они не едут; при «уменьшить движение» панель просто
    есть. Капсула при этом нажата, и тот же тап её и опускает; тап по
    самому кадру тоже закрывает панель, так что из неё есть два выхода.
    Тот же смах вниз по кадру её и поднимает, а по самой панели — опускает (TASK-540, спека 10.14.4);
    панель листается, и смах по ней вниз идёт в закрытие только от самого верха, а не из середины
    списка. Раньше этот жест закрывал просмотр, и одним жестом двух дел не делают: просмотр
    закрывают «Закрыть» в левом верхнем углу и смах от левого края, как на любом экране. Один запрос
    `GET /memories/:id/media/:mediaId` на открытие — кто принёс, когда и сколько всего
    кадров у него, файл и размер, размеры в пикселях, камера, место и в каких роликах кадр стоит и на
    какой секунде. Строка, для которой у сервера нет данных, не рисуется вовсе (`frameFacts` в
    `src/lib/frames.ts` — там же и правило, и его тесты); камеру, место и раскладку по роликам пишет
    montage-воркер, так что у старых кадров их нет, и это нормальное состояние панели, а не ошибка.
    Место — названием, а не числами: сервер отдаёт только координаты, а название по ним даёт
    встроенный в телефон определитель адреса (`reverseGeocodeAsync` из `expo-location`, без
    внешних сервисов и ключей; `src/lib/geocoder.ts`, сборка строки — `src/lib/place.ts`). Пока он
    не ответил, а также если не ответил, ответил пусто или упал — строка показывает координаты
    числами. Ответ помнится до закрытия приложения (в памяти, по координатам), в лог и на диск
    не пишется. На Android определитель работает только при выданном доступе к геопозиции, а
    приложение его не запрашивает: там строка всегда остаётся координатами.
    Права на геопозицию, которые `expo-location` приносит в манифест, заблокированы в `app.json`
    (`blockedPermissions`), чтобы приложение в магазине не выглядело просящим геопозицию, — Android
    показывает координаты, а не название: так принято, это не недоделка.
    Строка ролика ведёт в нынешний плеер воспоминания (`/memory/[id]?montage=…`);
    своего плеера у кадра нет. Имени у ролика пока тоже нет — строка зовёт его «Ролик на 1:00» из
    длительности.
    «Поделиться» отдаёт локальную копию через системный лист (`shareFile` в `src/lib/downloads.ts`,
    `expo-sharing` — на обоих телефонах), а не подписанную ссылку — она умирает через четверть часа.
    Копии лежат в отдельной папке кэша и после ответа листа не удаляются: ответ листа не значит, что
    приложение, куда файл ушёл, его уже прочитало (на Android лист отвечает, как только выбрано
    приложение). Прежние копии стирает следующее «Поделиться» перед тем, как скачать новые, — на
    телефоне остаётся только последняя пачка, а таймеров уборки нет. Закрытый лист ошибкой не
    считается; лист, который не смог открыться, пишется в лог. Удаление: своё удаляет каждый, чужое
    только организатор, но решает это `api`, экран лишь рисует строку меню; спрашивает он листом
    подтверждения кита с самим кадром и ценой словами, а не системным `Alert`. Забрать что-то домой, отдать наружу или удалить пачкой можно через режим выбора — та самая
    круглая кнопка в шапке. В нём капсула считает выбранное («Выбрано 4» / «38 МБ · 3 фото и
    1 видео», тап — выбрать все или снять), слева вместо «назад» встаёт кнопка лейблов (открывает
    листы лейблов, см. ниже; ничего не выбрано — выключена, как и кнопки подвала), а подвал меняется
    на «Поделиться · Скачать N · Удалить». Удаление спрашивает листом со счётом и удаляет только то, что человеку можно
    (свои кадры; у организатора любые) — решает это всё равно `api`. «Поделиться» пачкой открывает
    системный лист по файлу: `expo-sharing` берёт одно вложение за вызов. Листы идут один за другим
    (закрыл лист — скачивается и открывается следующий; оборвать цепочку можно только уйдя с
    экрана), а папка с копиями стирается один раз, перед первым файлом пачки (`shareFiles`), — не
    между листами: копию, только что отданную приложению, у него из-под рук не забирают. Пустой
    галерее не нужны ни кнопка выбора, ни фильтр с сортировкой, ни блок роликов: там только знак,
    две строки и «Добавить кадры» (`FramesEmpty`).

  заполненное остаётся и правится руками, а история, остановленная посреди печати, дописывается
  целиком. Каждый шаблон начинает с пустых истории, треков и длины — ничего от прошлого. Отмена —
  это не отмена таймера: у прогулки есть номер (`flight`), и после каждой паузы она спрашивает, всё
  ещё ли она текущая. При системном reduce-motion печати нет вовсе — поля заполняются целиком, пауза между
  шагами 400 мс. Считать умеет `src/lib/montage/order.ts` — он же и
  проверяется тестами: состояние мастера, отбор кадров и тело заказа (в исключённые уходит всё,
  чего в ролике не будет, — и снятое автоматом, и снятое рукой; возвращённое из автоотсева уходит
  в `include_media_ids`, иначе воркер снимет его снова; `music_tracks` шлётся всегда, пустой список
  — ролик без музыки; пожелание — у каждого трека своё, в `music_wishes` под ключом трека, и только
  непустое (общей `music_note` больше нет); длина — любое целое число
  секунд, и не сказали — значит api поставит своё). Границы длины и итог заказа считает только api
  (`POST …/montages/preview`), приложение — никогда. Автоотсев (`screening_rejected` на кадре)
  здесь — предложение: любой снятый кадр возвращается касанием или листом «Что сняли». Материала
  меньше трёх готовых кадров — поднимается лист «Материала пока мало» и ведёт на `upload`; проверка
  стоит над всеми шагами, а не после них. Тот же лист поднимает `409` на списке шаблонов: api
  взвешивает его как заказ без пожеланий и отказывает там, где счёт кадров не видит нехватки (три
  видео без измеренной длины — три кадра и ни секунды ролика). Свой трек уходит в R2 сразу при выборе (`src/lib/music.ts`),
  чтобы последняя кнопка была одним запросом. Полка из пяти слушается прямо на шаге музыки: ссылка
  подписывается на каждое нажатие (`GET /music/tracks/:id`), играет ровно один трек, повторное
  нажатие останавливает, а сам плеер принадлежит шагу — уход с него и есть тишина. Логика вынесена
  из экрана в `src/lib/music.ts` (`createPreview` / `useTrackPreview`) и проверяется без звука в
  `montage.test.ts`; сами экраны мастера читаются как текст в `tests/routes/order.test.ts`.
  Треков берут не больше 50 (`TRACK_LIMIT`: api отвечает `400` на 51-й; файл, который ещё
  грузится, своё место уже занял, а 51-й не берётся ни с полки, ни с телефона — шаг говорит это
  баннером) и в любом порядке — список и есть порядок проигрывания, меняется он
  перетаскиванием строки за имя (`movedTrack`). Строки разной высоты — с пожеланием под именем 60,
  без него 52, с открытым полем выше, — поэтому экран меряет каждую (`onLayout`), а куда ляжет
  строка, считает `landing` по этим высотам. Наверху всегда блок «Выбрано»: пустой — «ничего не
  добавлено» и «Ролик будет без музыки» (состояние, а не выбор — не нажимается), с треками — их
  строки, а отданный режиссёру — своё третье лицо, тоже состояние. Между блоком и полкой стоит
  карточка «На усмотрение режиссёра» (`CardDirector`, деталь 81): выбор и набор треков — одна ось,
  так что взяв карточку, отдаёшь список вместе с пожеланиями (api ответил бы 400 на пожелание к
  треку не из заказа), а плюс на полке снимает галочку и возвращает выбор к трекам; пока выбор за
  режиссёром, раздел «МУЗЫКА» гаснет до 40 %, но остаётся живым. В заказ уходит `music_director:
  true` на месте `music_tracks`, и слова о таком ролике читаются на итоге и в его сведениях
  (`trackWords`).
  Пожелание пишется к каждому треку отдельно: карандаш в строке раскрывает под ней поле
  (одно на экране), уход фокуса сворачивает его, и написанное встаёт подстрочником под именем, а
  карандаш заливается. Пожелание живёт на самом треке (`PickedTrack.wish`), поэтому убранный трек
  уносит его с собой (api отвечает 400 на пожелание к треку не из заказа), а переставленный —
  несёт. Длина на шаге «как собрать» — число
  секунд на ползунке: минимум и предел приходят из `preview` и перечитываются при каждой смене
  набора кадров и при каждом новом чтении материала (запрос упал — на месте ползунка баннер с
  «Повторить»), уже выбранная длина зажимается в новый предел, пресет длиннее предела не
  нажимается, а «из шаблона „…“» под числом снимается первым же ручным движением (`ownLength`).
  Итог (`summary.tsx`, шапка без шкалы, её счётчик — «Всё готово к монтажу») правит одно — имя
  ролика: заголовком итога стоит оно само (`NameHeading`, деталь 79, кегль подбирается под длину, на
  самом мелком — многоточие), тап — лист «Название ролика» (`FilmNameSheet`, тот же, что
  «Переименовать» на экране ролика). По умолчанию имя — шаблона (`s.montage.defaultName`), без
  шаблона — «Ролик на 2:30» по длине; с заказом уходят `template` и `name` (без шаблона и без правки
  имени не уходит, и api называет ролик по длине сам). Ничего другого итог не правит и ничего не
  считает: афишу, сводку и
  оценку времени он рисует по одному ответу `POST …/montages/preview`, посланному тем же телом,
  что и заказ, и спрашивает заново, если заказ под ним сдвинулся: после автопилота шаг 4 зажимает
  длину в предел, только когда придёт его собственный ответ. Кнопки нет, пока итог не совпал с
  тем, что она пошлёт. Отказ итога объясняется словами и ведёт кнопкой сразу на нужный шаг
  (`router.dismissTo`), а не назад по одному: `409` (мало материала) и `400` с `media_ids` (кадр
  из заказа удалили) — «К кадрам», `400` с `min_seconds`/`max_seconds` — «К длине». По пути
  материал читается заново (`reread` в `OrderProvider`): отказ — это api сказал, что почва
  сдвинулась, и шаг показывает то, что есть сейчас. Прочий `400` не ведёт ни на какой шаг — под
  ним, как и под сбоем сети или `500`, стоит «Повторить»: материал читается заново, и итог
  спрашивается телом из заказа как он есть. Других перечитываний у мастера нет — только это и
  «Повторить» после упавшего чтения. Любой сбой мастера — чтение материала, шаблоны, треки, длина,
  итог — говорит словами приложения на его языке, а не английской строкой api: разбирает его одна
  `refusal()` из `src/screens/order/wizard.tsx` (длина — с пределами из тела отказа, незнакомое тело —
  «Сервер ответил N»). Заказ — один
  `POST /memories/:id/montages` с итога, после него — ожидание над этим роликом. «Отмена» на любом
  шаге спрашивает подтверждение, если в заказе уже что-то есть (`entered()` в `src/lib/montage/order.ts`).
- **`profile` — Account** (`src/app/profile.tsx`, `Account` спеки, выгрузка 25 сентября) — карточка
  профиля (аватар 64, имя, ник, почта, карандаш), раздел «Контакты» (стопка лиц и «N человек»; пока
  никого нет или список не прочитался — ни счёта, ни лиц, только «Зовите выбором, не по нику»), «Тема»
  и «Язык» сегментами без пояснений, раздел «Галерея» с тумблером «Даты между днями» — настройкой
  аккаунта (`useAuth().setDatesBetweenDays`, отказ api откатывает тумблер и встаёт баннером) — и
  внизу красная «Выйти из аккаунта», которая спрашивает мягким листом подтверждения. Карандаш меняет
  только ник (doc-04: имени и аватара продукт не хранит): та же `UsernameForm`, что на `set-username`,
  листом поверх экрана. Не переходом на `set-username`: гейт объявляет его только аккаунту без ника.
- **`about` — About** (`src/app/about.tsx`) — показывает текущий `EXPO_PUBLIC_API_URL`. Ссылки на
  него в приложении нет: в ките шапка главного экрана держит один значок справа, и это профиль.
  Экран остаётся в навигаторе и открывается маршрутом (`/about`).

Весь HTTP — в `src/api/`, состояние сессии — в `src/lib/auth.tsx`.

### Очередь загрузки

Отправка файлов в R2 живёт в `src/lib/upload/send.ts` — не в экране: загрузка переживает и уход с экрана, и
перезапуск приложения. По файлу: `POST /memories/:id/media` (ссылки на части, и в этой же заявке —
`file_name`, имя файла на телефоне: другого источника у «сведений о кадре» нет; режется до 255, как
просит `api`), `PUT` кусками прямо в R2 мимо `api`, `POST …/complete` в конце. Что R2 уже принял, помнится по etag'ам частей, поэтому
обрыв догружается, а не начинается заново; протухшая через час ссылка перезапрашивается тем же
`GET …/upload` — тот же `upload_id`, уже залитое остаётся. Так же, один раз за проход, заново уходит
кусок, на который хранилище не ответило: связь оборвалась или ответа нет дольше `partDeadline`
(`queue.ts`: 30 секунд плюс время куска на 256 кбит/с — у целых 8 МиБ без малого пять минут).
Очередь лежит в `uploads.json` в documents (`expo-file-system`) и перечитывается на старте; пустая
очередь ничего не делает.

Заводится хук `useUploads()` — один раз в корне приложения, не дожидаясь ни шрифтов, ни навигатора
(чтобы очередь подхватилась на любом экране), и ещё раз там, где она показана: на `upload`/`queue`
и на «Мои кадры». У файла в очереди есть `uri` — картинка из галереи телефона для плитки «летит».
Повтор после обрыва — сам, по таймеру: через 15 секунд после того, как очередь встала, и никогда
раньше. Возвращение в приложение (`AppState`) повтор не делает, а заново заводит этот отсчёт: iOS
уходит в неактивное и обратно от шторки уведомлений и системных вопросов, и повтор на каждый такой
раз мигал застрявшим файлом (TASK-413). Двадцать пауз подряд без единой ушедшей части — и очередь
сама больше не пробует, до «Повторить» на экране (он повторяет сразу) или возвращения в приложение.
Ссылок нигде не храним: они живут час, а на возобновлении всё равно запрашиваются заново.

Арифметика частей (что нарезать, что уже принято, сколько процентов) — в `src/lib/upload/queue.ts`,
отдельным чистым модулем: это и есть докачка, и она проверяется тестом без телефона.

Причина, по которой файл встал, в очереди хранится строкой-причиной (`UploadFailure` там же), а не
готовым текстом: очередь лежит на диске и переживает и смену языка, и перезапуск. Текст собирает
`failureText(s, …)` в момент отрисовки баннера. Готовых фраз в очередь не кладём — иначе они
застревают в языке, в котором были написаны. Перечитанные со старта причины сбрасываются: они
относятся к прошлому запуску, и повтор скажет, что не так сейчас. Причина называет, где сломалось, и
«не достучались до сервера» (`offline`) — только про вызов `api`, который остался без ответа.
Хранилище — `partRefused` (ответило отказом) и `storageOffline` (не ответило, с кодом, если он успел
прийти); сам файл на телефоне — `gone` (в галерее его больше нет), `unreadable` (телефон файл не
отдал: за записью ничего нет, разрешение отозвано или байты не читаются) и `iCloud` (оригинал лежит
в iCloud и не скачался сейчас). Исходная ошибка каждого такого сбоя уходит в лог (`console.warn`) там,
где её поймали (TASK-413).

У `unreadable` и `iCloud` есть `detail` — шаг, на котором телефон отказал, и что он ответил, слово в
слово (`read part 1: …`, `no localUri, isNetworkAsset …`, `getAssetInfoAsync, download off: …`). Он
стоит в скобках на строке застрявшего файла и уходит в лог `api`: запросом
`GET /health?upload_failure=…&detail=…&file=…&memory=…&media=…&platform=…` — отдельного маршрута
под это нет, а Fastify пишет в лог каждый адрес вместе с параметрами. Искать в логе пода `api` по
`upload_failure`; по строке на файл и причину за запуск, не на каждый повтор (TASK-434).

Оригинал из галереи открывается только на чтение (`open(FileMode.ReadOnly)`): без режима
`expo-file-system` открывает `file://` на чтение и запись, а файл галереи приложению дают только
читать. Симулятор этого не проверяет — там приложение не заперто, и запись ему разрешена.

Снимок из iCloud — не сбой, а ожидание: при включённой «Оптимизации хранения iPhone» (обычное
состояние забитого телефона) за записью в галерее лежит только уменьшенная копия, а оригинал надо
сначала скачать. Поэтому запись спрашивается дважды (`sourceFile` в `send.ts`): сперва с
`shouldDownloadFromNetwork: false` — только в этом режиме iOS заполняет `isNetworkAsset`, то есть
это единственный ответ, который отличает снимок из iCloud от файла, который правда не читается (со
включённой докачкой оба приходят одинаково: запись без `localUri` и без объяснений), — а потом, если
файла на телефоне нет, со включённой: этот вызов и есть скачивание. Второй вопрос уходит независимо
от флага: оригинал, который iOS не назвала облачным, а локально всё равно не отдала (общий альбом,
отменённый запрос), стоит одной попытки; флаг решает, что скажут человеку, а не стоит ли пробовать. Пока оно идёт, у файла в очереди стоит
`cloud`, и блок отправки говорит «Кадр подгружается из iCloud» вместо «Отправляем»; процента система
не сообщает, поэтому это состояние, а не цифра. Не скачалось — файл встаёт с причиной `iCloud`, а не
объявляется нечитаемым: iOS продолжает скачивание в фоне, и очередь своей паузой вернётся к этому
файлу (TASK-419).

Обратная дорога — `src/lib/downloads.ts`: разрешение медиатеки, скачивание в кэш, сохранение в
галерею телефона и уборка кэша за собой. Ею пользуются оба экрана, которые что-то кладут на
телефон, — галерея (оригиналы) и экран монтажа (готовый ролик).

### Журнал монтажа

Рассказ режиссёра о том, как собирается ролик, живёт в `src/lib/montage/journal/` — отдельно от
экранов, как и арифметика заказа: всё чтение и все выводы проверяются без телефона
(`montage-journal.test.ts`, ответы записаны по форме из README api). Тот же слой и три экрана
журнала проверены и на настоящих ответах: `tests/recorded-api/` — записанные ответы api по двум
настоящим сборкам воркера, проигранные через клиент и экраны без сети (откуда они и как
обновлять — `tests/recorded-api/README.md`).

Читается одним хуком — `useMontageJournal(token, memoryId, montageId, { stage })`. Пока
ролик в очереди или в работе, он опрашивает `GET …/journal` раз в 1.5 секунды; курсор — наибольший
`id` отданной порции, и при `has_more` следующая порция запрашивается сразу, в том же опросе, а не
через полторы секунды: между двумя опросами может лечь больше записей, чем влезает в порцию, и
«самые свежие» оставили бы в середине дыру. Готовый или упавший ролик не опрашивается вовсе, экран
не в фокусе или приложение в фоне — опрос стоит и возобновляется чтением при возвращении. Обрыв
связи ничего не стирает: прочитанное остаётся, а `standing` становится `offline` до первого
удавшегося опроса. 404 — не обрыв: так api отвечает тому, кого в воспоминании нет или кого убрали
посреди просмотра; `standing` становится `refused`, опрос встаёт до возвращения экрана, а живой
экран и журнал этапа вместо журнала показывают баннер «Вас больше нет в этом воспоминании» — как
листы лейблов, и везде со знаком разорванной связи (`unlink`), а не «нет сети» — это не про связь.
Назад по журналу — `loadOlder()`, по одной порции на зов. Упавший ролик
поставлен заново — `restart()`: api стёр журнал прошлой попытки, и хук читает его с нуля.
Повтор, начатый не этой кнопкой, — воркер сам повторил задачу после сбоя или организатор нажал
«Повторить» на другом телефоне, — хук замечает по ответу (`startedOver`): этап, который он видел
начатым, пришёл с другим `started_at` или пропал вовсе. Начало этапа воркер пишет раз за попытку и
стирает только в начале новой, а повтор через api стирает этапы целиком; ход сборки, падение и
«готов» его не трогают. Тогда прочитанное выбрасывается и журнал в том же опросе читается с начала,
как после `restart()`, — записей прошлой попытки на экране не остаётся. Сорвавшийся ролик не
опрашивается, поэтому повтор с другого телефона виден, когда экран вернулся в фокус.
Раскладку кадров (`places`) воркер делает только на этапе `music`, а api присылает файл лишь вместе
с новой записью о нём — поэтому журнал этапа, читанный во время сборки, в момент «готов» один раз
перечитывается с начала тем же сужением ради `files` (`relaid`). Весь журнал так не перечитывается:
экран ролика на «готов» уходит на страницу ролика, а та читает журнал заново — одной порцией: этапы
там свёрнуты в пять строк списка, и ей нужны только они — сколько собирали и чем кончился каждый.

Всё, что экран берёт из ответа, посчитано там же: какой этап идёт (`currentStage`, `stageNumber`),
что в руках у режиссёра (`inHand`), «осталось ≈ N мин»
(`minutesLeft`), строка под именем этапа (`stageLine`, `stageMinutes`) и её состояние для строки
(`stageStanding`), рамка «куда
смотрит» в точках картинки (`gazeAt` — доли 0..1 превращаются в левый верхний угол квадрата: 100 на
карточке «Сейчас», 114 на листе файла — как в макете вместе с обводкой; 96 и 110 спеки — CSS-коробка
внутри обводки 2), чипы журнала (`sifted` — режет по `decision`, ровно так же,
как api считает `taken_count` / `skipped_count` / `thought_count`), где кадр лёг в ролике
(`placeLine` — по раскладке файла, а не по мысли; у клипа, взятого несколькими отрезками, i-я запись
«беру» — его i-е место в ролике, `takenBefore`) и пилюли решения словами (`marksOf`,
`reasonWord`; у «Беру» по слову организатора рядом стоит «Взят по слову организатора» — `whyTaken`,
на журнале этапа и в листе файла). Печать мысли —
`useTypedThought(text, fresh)`: допечатывается только запись, пришедшая при открытом экране
(`isFresh`), при «уменьшить движение» фраза появляется целиком. Хук отдаёт две половины — `said` и
`unsaid`, — и кит кладёт вторую невидимой: фраза с первой буквы занимает свою высоту, и то, что под
ней, не едет. Слова этапов, решений и причин — в
`s.montage.stage` и `s.montage.live`.

Экранов у журнала четыре, и все стоят на этом хуке:

- **`memory/[id]/montage/[montageId]` — The film, in any of its five states**

### Как добавить экран за входом

Гейт — `Stack.Protected` в `src/app/_layout.tsx`; ключ к нему — `status` из `useAuth()`. Экраны
не прячутся, а **не существуют**: `expo-router` выкидывает из навигатора всё, что гейт не пустил.

| `status`         | Какие экраны существуют                                            |
|------------------|--------------------------------------------------------------------|
| `loading`        | `login`, `login/email`, `login/code` — под сплэшем, чтобы холодному старту было где стоять |
| `signed-out`     | `login`, `login/email`, `login/code`                               |
| `needs-username` | `consent`, `set-username` — в этом порядке: соглашение стоит перед ником, и первый объявленный экран и есть тот, на который гейт приземляет |
| `ready`          | `index`, `create`, `profile`, `about`                              |

Новому экрану за входом нужны **две** вещи: файл в `src/app/` и строка в блоке `status === 'ready'`.

```tsx
<Stack.Protected guard={status === 'ready'}>
  <Stack.Screen name="memories" options={{ title: 'Memories' }} />
</Stack.Protected>
```

Забыли вторую — маршрута **молча** не будет: переход по нему не упадёт с ошибкой, а уведёт на
первый экран, который всё-таки объявлен.

Текущий пользователь — `const { user, token } = useAuth()`; за гейтом он уже загружен, и `token`
не `null`. Вызов API — новая функция в `src/api/`, которая принимает `token` параметром;
заголовок `Authorization: Bearer` вешает сам `request`:

```ts
export function listMemories(token: string): Promise<Memory[]> {
  return request('/memories', { token });
}
```

Ошибку с такого вызова показывают через `errorMessage(error)` — она достаёт формулировку самого
API. Ветвиться на конкретный ответ (`403`, `409`) можно по `error instanceof ApiError` и
`error.status`.

`401` на вызов с `token` экран не разбирает: это api перестал признавать сессию (вышли на другом
телефоне, отозвали, прошли 30 дней), и `request` сам говорит об этом `AuthProvider`
(`onSessionRefused`) раньше, чем ошибка дойдёт до экрана. Тот сбрасывает вход тем же `forget`, что
и «Выйти», только без `POST /auth/logout` — один раз, сколько бы опросов ни получили `401` разом, —
и гейт уводит на `login`: экраны за входом перестают существовать, их опросы — вместе с ними.
`401` входа (`/auth/email/verify`, `/auth/apple`, `/auth/google`) идёт без токена и остаётся
ответом экрану, который спросил.

## Команды

| Команда | Что делает |
|---|---|
| `npx expo start` | dev-сервер: Expo Go, симулятор, эмулятор |
| `npm run ios` / `npm run android` | то же, сразу открыть симулятор/эмулятор |
| `npm run typecheck` | `tsc --noEmit` |
| `npm test` | vitest, один прогон |
| `npm run lint` | biome: линтер и проверка формата, предупреждение — тоже отказ |
| `npm run format` | biome: привести формат |
| `npm run update:dev` | выложить обновление по воздуху в канал `dev` — см. «Обновления по воздуху» |

Формат и линт — `biome`: один инструмент на оба, тот же, что в `api`. Что выключено и почему —
написано в `biome.jsonc` строкой над каждым правилом; выключено там только то, что это правило
читает неверно (`role` у кита — типографика, а не ARIA) или что в тесте и есть норма. Корневой
`make check` зовёт отсюда `npm run lint` и `npm run typecheck`.

### Работа в изолированной копии (git worktree)

Изолированная копия агента — это `git worktree` внутри `.claude/worktrees/`. Проверки в ней
запускаются сами, руками ничего готовить не надо: `node_modules` в копии нет, и не нужно — Node
ищет его в родительском каталоге, а worktree лежит внутри него. Если родительскую копию
перенесли или поставили пакеты не там, `npm ci` в родительской копии — и всё.

Симлинк на чужой `node_modules` не ставьте: `npm install` его сносит («Removing
non-directory») и ставит на его место свой каталог, после чего копия молча разошлась с той, что
рядом. Ставить пакеты нужно в родительской копии — копия подхватит.

`npm run lint` в копии проверяет те же файлы, что и обычно. В `biome.jsonc` нет исключения
`**/.claude`: node догадывается о нём по самому пути и, сидя внутри `.claude/`, не проверяет
ничего — выходит с кодом ошибки на пустом месте. Рабочие копии и так не входят в проверку,
их отсекает `.gitignore` (`.claude/worktrees/`) через `vcs.useIgnoreFile`.

Тесты лежат в `tests/` и нигде больше — той же раскладкой, что `src/`. Общие помощники и фикстуры
— в `tests/helpers/`, и импортируются как `@tests/helpers/…`.

## Чего здесь нет

CI, профиль EAS для прода, стейт-менеджер — всё это принесёт та фича, которой понадобится. Экраны на пилоте проверяются
руками: vitest здесь под чистую логику вроде `src/lib/media-window.ts`, под истории деталей и под потоки
экранов через `react-test-renderer` (экран с поддельным `fetch`).
Второе держится на одном алиасе в `vitest.config.mjs` — `react-native` в тестах подменяется на
`react-native-web`, — и отвечает только за разметку: сколько кадров нарисовала карточка и что она
показывает, когда их нет. Что нативный `Image` делает с подписанной ссылкой, из node не видно.

Нет и веб-сборки как мишени для проверок. `npm run web` (`expo start --web`) из `package.json` не
убран и запускается, но проверять продукт в браузере нечестно: единственный клиент — телефон, iOS и
Android, и под паритет с ним веб не чинится. Проверяйте на симуляторе, эмуляторе, в Expo Go или
dev-билде — как описано в «Запуске» выше.

В браузере отваливаются ровно две вещи, которых на устройстве нет:

- **Вход не сохраняется.** `src/lib/auth.tsx` кладёт токен в `expo-secure-store`
  (`SecureStore.setItemAsync`/`getItemAsync`, ключ `session-token`), а на web это пустая заглушка —
  сессии просто негде остаться.
- **Запросы к API не уходят.** Сервер не отдаёт браузеру заголовков доступа (CORS) — он их и не
  должен, клиентов-браузеров у продукта нет.

Оба выглядят как блокеры продукта и оба уже стоили времени на поиск несуществующего бага. Алиас
`react-native-web` выше к этому отношения не имеет: он живёт только в vitest под node.
