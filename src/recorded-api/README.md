# Записанные ответы api — сквозной тест журнала монтажа

Здесь лежат ответы маршрутов журнала и списка роликов, записанные api по двум **настоящим** сборкам
воркера: с нейросетью-режиссёром (`responses_director.json`) и без неё, отсев и ритм
(`responses_algorithm.json`). Приложение проигрывает их через свой настоящий клиент и настоящие
экраны — без сети, ключей и стенда: `journal-data.test.ts` (слой данных, `@/montage-journal` и
клиент `@/api`) и `journal-screens.test.tsx` (экраны «Монтаж идёт», журнал этапа, карточка файла,
«Ролик готов» / «Как собирался», лента роликов), `journal-failed.test.tsx` — сорвавшийся ролик
(экран без признаков эфира, карточка с причиной), а `journal-session.test.tsx` — тот же опрос под
настоящей сессией (`@/auth`), когда api посреди сборки перестаёт её признавать, а
`journal-restart.test.tsx` — тот же опрос, когда сборку начали заново под открытым журналом.
`recorded.ts` —
загрузка записей и подмена `fetch`, которая отвечает по запросу (кто спросил, какой маршрут, какой
курсор), а не по порядку вызовов; запрос, на который ответа не записано, падает и попадает в
`unmatched`.

## Откуда и что это

Файлы — **копии** записей api: `projects/api/src/montages/golden/responses_*.json`. Формат
(`format: 1`, шаги `steps` по времени, нормализация id и ссылок) описан в README api, раздел
«Журнал монтажа — снимки и записанные ответы». Что в них настоящее: записи журнала, итоговые
этапы и раскладка кадров — вывод воркера. Смоделировано тестом api то, что лежит между ними: как
строки этапов меняются по ходу сборки (ниже) и какие числа стоят в них до «готов» — оценки и
счётчики; порядок и набор шагов — как ведёт воркер (`journal.py`, `montage.py`).

Чего в записи нет и что тест дописывает сам, поэтому это не «слова api»:

- ответы на `before=` (лента этапа листается назад, зритель дочитывает середину), на `stage=`
  (журнал одного этапа) и на чтение этапа с `after` («с начала», как перечитывает журнал этапа при
  «готов») — нарезаются из записанного целого журнала готового ролика по правилу из README api
  (`recorded.ts`, `cutFrom`, а по ходу сеанса — `moments`: записи, этапы и файлы такими, какими
  их успели сказать записанные шаги, и настоящими файлами с раскладкой на «готов»); записанного
  poller'а таких запросов не было. Это нарезка, а не слова api;
- журнал в сотни записей («Ролик готов», `cutEvery` в `recorded.ts`): записанный журнал готового
  ролика — одна порция, поэтому тест повторяет его записи этап за этапом под своими `id` и множит
  счётчики этапов, а каждое чтение, и первое несуженное тоже, нарезается из этого целого по тому же
  правилу. Это размножение и нарезка, а не слова api;
- сорвавшийся ролик (`fellOver` в `recorded.ts`): записи такого нет, поэтому список, снятый на
  втором этапе, и журнал готового ролика урезаются до падения на этом этапе, с причиной воркера
  или без неё; пять этапов остаются пятью — три после упавшего такие, какими воркер их завёл
  (`live_first_open_empty`). Это нарезка, а не слова api;
- сбои чтения (401, 404, 500, обрыв сети) — `refuse` в `recorded.ts`; записанным остаётся только 404 посторонему;
- повтор сборки (`journal-restart.test.tsx`): в записи одна попытка, поэтому после «Повторить»
  (`queued`, ни этапов, ни записей), упавшая попытка и сама вторая попытка — записанный сеанс,
  сказанный заново с `id` после наибольшего первой и этапами, начатыми на час позже, — собраны
  тестом из записанных ответов. Ответ сразу после начала новой попытки (пять этапов в ожидании,
  записей нет) — это записанный `live_first_open_empty`, слов тест не дописывает;
- `/memories` и список участников — имена людей, которых журнал называет по id; `/me` — кто стоит за
  токеном организатора, для сессии.

### Модель этапов в записи

Воркер (`journal.begin`) заводит **все пять этапов сразу**, в самом начале сборки, до первой записи:
`pending`, `started_at` пуст, `done_count` 0, `total_count` пуст, у каждого — оценка `eta_seconds`.
Дальше строки только **меняются**, никогда не «появляются». Поэтому во всех живых шагах — те же
пять строк в порядке конвейера, а приложение считает «Этап N из 5» и «осталось ≈» именно по такой
модели:

| Шаг | Что в этапах |
|---|---|
| `live_first_open_empty` | экран открыли до первой записи: пять `pending` с оценками, записей нет, курсор `0`. Приложение не называет этап и не обещает время — пока не начат ни один |
| `live_poll_1` | отсев `running`, `done_count` = `total_count` (13; в algorithm 12), оценка 0 — счётчик доходит до конца раньше, чем воркер закрывает этап; остальные четыре `pending` |
| `live_poll_2` | отсев `done`, остальные `pending` |
| опросы «разбора» | `understanding` `running`, `done_count` 0, оценка **та же, что в `begin`**: до `done` она не убывает; `directing`, `rhythm`, `assembly` `pending` |
| опросы «режиссёра» (и `live_viewer_opens_mid_build`) | `directing` `running`, `done_count` 0, оценка неизменна; записи ложатся порциями по пять, счётчик их не считает |
| хвост опросов без записей | ритм `running` → ритм `done` → склейка `running` (0 из N, оценка с `begin`) → склейка на середине (пересчитана) → склейка `done`. В director это `live_poll_13…17`, в algorithm `live_poll_11…15` |
| `montage_list_while_building` | список пока сборка идёт: у собирающегося пять этапов со своим `state` (без счётчиков и оценок), у ждущего и старого готового `stages: null` |

Записи ложатся порциями по пять, опрос идёт с `limit=4`, поэтому после порции `has_more: true`, а
следующий опрос отдаёт хвост. Опросы с курсором `after`, где новых записей нет, отдают `files: []`:
раскладка кадров ложится после всех записей, и её видно только при перечитывании (приложение
перечитывает журнал один раз, когда этап-экран видит «готов»).

Что из этого приложение **не** должно перепутать, и что теперь держат тесты: этап «не появляется»
(номер считается по пяти строкам, а не по их числу); `pending` — не достигнутый этап; оценка идущего
этапа не убывает, и «осталось ≈» не растёт и не уходит ниже минуты, пока хоть один этап не `done`;
`running` при `done_count` = `total_count` — ещё не «готово»; карточка ленты (пять этапов со
`state`) и экран (пять строк журнала) называют один и тот же этап на каждом шаге записи.

Одна проверка из этих **красная намеренно**: у «разбора» и «режиссёра» воркер не двигает счётчик —
он стоит на нуле весь этап, — а строка под названием этапа пишет «0 из 13», пока под ней ложатся
записи (`journal-data.test.ts`, «a stage at work does not say «0 из N»…»). Это изъян приложения на
верной модели, а не теста: строка читает `done_count` как «сколько сделано» там, где воркер его не
ведёт. Когда приложение поправят, этот абзац убрать.

## Как обновлять

Записи перезаписывает api, когда меняется вывод воркера или то, как api его отдаёт. После этого:

```sh
cp ../api/src/montages/golden/responses_*.json src/recorded-api/
npm test -- src/recorded-api
```

Копировать `cp`, не переформатируя: тогда разница с оригиналом — ровно то, что изменилось в
ответах. Тесты выводят почти всё из самих записей, поэтому изменение чисел проходит зелёным, а
изменение **модели** (этапы снова заводятся по одному, оценка убывает) ловят только сторожевые
проверки в `journal-data.test.ts` — читай diff записей, а не только итог прогона. **Молчаливого разъезда между репозиториями не устранить**: api перезаписал записи, а
здесь их не обновили — тест зелёный на старых ответах. Условие связи, а не ошибка теста; если
api сказал, что ответы изменились, — это повод скопировать их и прогнать набор.

## Как писать тест, чтобы он не валил соседей

Тест, идущий по журналу удар за ударом (`tick`, много `act`), берёт `act`, `drives()`, `settle` и
`BEAT_BY_BEAT` из `src/test-drive.ts`, а не `act` из `react-test-renderer`: vitest не умеет
остановить тело теста, когда время вышло, и его хвост продолжал двигать часы и `act` следующих
тестов — падал весь остаток файла. `act` оттуда не стартует после таймаута, `drives()` (после
собственных хуков файла) ждёт уже идущий `act`. `BEAT_BY_BEAT` (20 с) — только таким тестам: в
покое они идут 0,1–0,5 с, под нагрузкой в 50 — до 4 с, а пять секунд vitest — орлянка. Тест, который
трогает дерево раз-другой, оставляет предел по умолчанию.
