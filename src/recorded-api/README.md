# Записанные ответы api — сквозной тест журнала монтажа

Здесь лежат ответы маршрутов журнала и списка роликов, записанные api по двум **настоящим** сборкам
воркера: с нейросетью-режиссёром (`responses_director.json`) и без неё, отсев и ритм
(`responses_algorithm.json`). Приложение проигрывает их через свой настоящий клиент и настоящие
экраны — без сети, ключей и стенда: `journal-data.test.ts` (слой данных, `@/montage-journal` и
клиент `@/api`) и `journal-screens.test.tsx` (экраны «Монтаж идёт», журнал этапа, карточка файла,
«Ролик готов» / «Как собирался», лента роликов), `journal-failed.test.tsx` — сорвавшийся ролик
(экран без признаков эфира, карточка с причиной), а `journal-session.test.tsx` — тот же опрос под
настоящей сессией (`@/auth`), когда api посреди сборки перестаёт её признавать. `recorded.ts` —
загрузка записей и подмена `fetch`, которая отвечает по запросу (кто спросил, какой маршрут, какой
курсор), а не по порядку вызовов; запрос, на который ответа не записано, падает и попадает в
`unmatched`.

## Откуда и что это

Файлы — **копии** записей api: `projects/api/src/montages/golden/responses_*.json`. Формат
(`format: 1`, шаги `steps` по времени, нормализация id и ссылок) описан в README api, раздел
«Журнал монтажа — снимки и записанные ответы». Что в них настоящее: записи журнала, итоговые
этапы и раскладка кадров — вывод воркера; этапы «в работе» между ними смоделированы тестом api.

Чего в записи нет и что тест дописывает сам, поэтому это не «слова api»:

- ответы на `before=` (лента этапа листается назад, зритель дочитывает середину), на `stage=`
  (журнал одного этапа) и на чтение этапа с `after` («с начала», как перечитывает журнал этапа при
  «готов») — нарезаются из записанного целого журнала готового ролика по правилу из README api
  (`recorded.ts`, `cutFrom`, а по ходу сеанса — `moments`: записи, этапы и файлы такими, какими
  их успели сказать записанные шаги, и настоящими файлами с раскладкой на «готов»); записанного
  poller'а таких запросов не было. Это нарезка, а не слова api;
- журнал в сотни записей («Ролик готов», `cutEvery` в `recorded.ts`): записанный журнал готового
  ролика — одна порция, поэтому тест повторяет его записи этап за этапом под своими `id` и множит
  счётчики этапов, а каждое чтение, и первое несуженное тоже, нарезается из этого целого по тому же
  правилу. Это размножение и нарезка, а не слова api;
- сорвавшийся ролик (`fellOver` в `recorded.ts`): записи такого нет, поэтому список, снятый на
  втором этапе, и журнал готового ролика урезаются до падения на этом этапе, с причиной воркера
  или без неё. Это нарезка, а не слова api;
- сбои чтения (401, 404, 500, обрыв сети) — `refuse` в `recorded.ts`; записанным остаётся только 404 посторонему;
- `/memories` и список участников — имена людей, которых журнал называет по id; `/me` — кто стоит за
  токеном организатора, для сессии.

## Как обновлять

Записи перезаписывает api, когда меняется вывод воркера или то, как api его отдаёт. После этого:

```sh
cp ../api/src/montages/golden/responses_*.json src/recorded-api/
npm test -- src/recorded-api
```

Копировать `cp`, не переформатируя: тогда разница с оригиналом — ровно то, что изменилось в
ответах. **Молчаливого разъезда между репозиториями не устранить**: api перезаписал записи, а
здесь их не обновили — тест зелёный на старых ответах. Условие связи, а не ошибка теста; если
api сказал, что ответы изменились, — это повод скопировать их и прогнать набор.
